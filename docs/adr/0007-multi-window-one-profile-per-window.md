# Multiple Windows, each bound to exactly one Profile

A **Window** is a Tauri `WebviewWindow` — an OS-level application window. The app supports an arbitrary number of Windows running concurrently inside the same process. Each Window owns exactly one **Profile**, and each Profile is owned by at most one Window at a time; ownership is exclusive for the duration a Window is open. The File menu carries a "New Window with Profile" submenu listing Profiles not already open (each disabled when owned elsewhere) plus a "New Untitled Profile…" footer that creates a fresh Profile auto-named `Untitled` (or `Untitled N` on collision) and immediately opens it in a new Window. The existing "Switch Profile" submenu remains — switching within a Window closes that Window's Opened workspaces and reuses the same OS Window; opening in a new Window is additive and leaves the current Window untouched. There is no plain "New Window" without a Profile: the user must always pick one, because the alternative ("auto-pick the first unopened profile") is too surprising for a feature whose only purpose is putting *specific* contexts in front of the user.

The "exclusive ownership" rule is the design decision that keeps the rest of the architecture from rippling. With one Profile per Window:
- Every existing per-store singleton (`useWorkspaceStore.activeWorkspaceId`, `usePtyActivityStore.openedWorkspaceIds`, `useWorkspaceStore.focusedPaneId`) becomes per-Window *for free* — each Window has its own JS context and so its own Zustand store instance.
- The PTY ownership model stays singleton — one PTY, one xterm.js renderer, one DOM tree. We considered allowing a Profile to be open in multiple Windows simultaneously and rejected it: PTYs cannot be rendered into two xterm.js canvases, layout writes from two Windows would race on `tabsApi.update`, and a cross-Window pessimistic-lock layer is meaningful engineering for a marginal "same workspace, two screens" UX win.
- Profile deletion stays scoped to one Profile + its Workspaces. The "strict" deletion rules — forbid deleting a Profile owned by another Window, forbid deleting the current Window's active Profile when no unowned profile exists to auto-switch into — are extensions of the existing ADR-0006 invariant "at least one Profile must exist," generalised to "at least one Profile available to *this Window* must exist." Permissive deletion (cascade-close the other Window, or yank its Profile and force it to auto-switch) was rejected because it introduces non-local effects — a user clicking Delete in one Window destroys agent state in another Window they weren't even looking at, which is the kind of surprise that erodes trust.

The Rust side gains a single new piece of state: `ActiveProfileState` is upgraded from `Mutex<Option<String>>` (one app-wide active id) to `Mutex<HashMap<WindowLabel, ProfileId>>`. Every `set_active_profile_id` IPC command takes the calling Window's label (Tauri injects the Window into command parameters) and updates only that Window's entry. Every "open new Window with Profile X" path atomically checks the map for an existing owner of X before assigning. The native menu rebuild also reads from this map: the "Switch Profile" submenu's checkmark reflects the *focused* Window's active Profile, and the "New Window with Profile" submenu dims entries whose ids appear in the map under a Window other than the focused one. Menu rebuilds are triggered both on Profile CRUD (as before) and on Window focus change (new). On macOS this matters most — the menu bar is global and switches as the user `Cmd+`-tabs between Windows.

The frontend's `activeProfileId` moves *out* of `localStorage`. localStorage is shared across all Windows of the same origin, so storing per-Window state there would have each Window clobber the others. Instead, each Window's `profileStore.activeProfileId` is initialised by an IPC call (`getActiveProfileForWindow`) on startup; the Rust side is the source of truth. Global settings — theme, font, custom agents, GitHub identity — stay in localStorage; they are deliberately not per-Window today, consistent with ADR-0006's narrow Profile scope.

On launch, the app restores every Window from `windows.json` (a new file alongside `abundio.db` in the app data directory) containing `[{ label, profileId, lastFocused }]`. `tauri-plugin-window-state` already handles per-label window position/size, so each Window's geometry is preserved by labelling. On quit (which happens when the last Window closes, uniformly across platforms — rejecting the macOS "stay alive with no windows" convention for simpler menu state-machine reasoning), `windows.json` is written atomically before the final Window destroys. If `windows.json` contains a Profile that no longer exists, that Window is dropped; if two entries claim the same Profile (defensive — should not happen), only the first is honoured. If `windows.json` is missing or empty, the app starts with one Window on the position-order-first Profile.

Entry points are deliberately limited to the File menu. The command palette gains *no* "Open in New Window: X" entries; the existing `Profiles` palette category continues to mean "switch in this Window." This asymmetry is intentional: in-Window switching is frequent and benefits from a fuzzy-typed shortcut, while opening a new Window is a rare, OS-level structural action that wants the deliberation of a menu click. There is also no keyboard shortcut for "New Window" — Cmd+N would have to either open a picker modal (a new UI surface) or do nothing useful, and neither pays for itself.

## Consequences

- `activeProfileId` is removed from the `settingsStore` localStorage partition. Any existing user's persisted `activeProfileId` is ignored — they get the first Profile in position order on first launch under this build. (The migration is a non-event because the value was always reconcilable against the persisted Profile list; this is just letting the reconciliation happen once more.)
- `windows.json` becomes part of the app's persisted state. Corrupting or hand-editing it can produce surprising start-up window arrangements, but cannot harm the SQLite DB; it is read-only-by-default with replace-on-quit semantics. Backups are not warranted.
- The native menu rebuild fires more often: on Profile CRUD (already), on Window focus change (new), and on Window open/close (new). Each rebuild reads `ActiveProfileState` and the focused Window's label. The rebuild is fast enough that even fast Cmd+`-tabbing should not be perceptible.
- Settings panel's profile-list "Delete" button gains two distinct disabled states with different tooltips: `"Open in another window"` and `"No other profile available — create one or close another window first"`. Buggy UI here is recoverable (the backend rejects the IPC regardless), but the tooltips matter for the user understanding *why* an action is blocked.
- Closing the last Window quits the app on every platform. macOS users who expect "Cmd+W keeps the app alive" will be momentarily surprised; the trade-off is a simpler menu/state-machine — the menu never has to render "no windows, but app alive" mode.
- The PTY manager continues to be a single app-wide instance shared across Windows (Tauri-managed state is per-app, not per-Window). PTYs spawned by Window A are not visible to Window B even though both share the manager — visibility is gated by Pane id, and Panes never appear in two layouts. This is the same isolation the single-Window app already provides between workspaces; the multi-Window case piggy-backs on it.
- Future scope expansion (per-Profile theme, agents, GH identity) lands in the same place: each Window is already the right rendering boundary for "this Profile's theme." The Window/Profile binding is the seam any future per-Profile work hangs off of.
