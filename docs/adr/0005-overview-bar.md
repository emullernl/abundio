# Overview bar lives between Titlebar and workspace stack, reuses per-workspace PR fetch

The **Overview bar** is a horizontal strip across the top of the window showing eight glanceable counts — Opened workspaces (out of total), the five Agent states (Idle, Working, Waiting, Ready, Error) aggregated across all Opened workspaces, plus the user's account-wide GitHub "review requested" and "my open" PR counts. It renders once in `App.tsx` between `<Titlebar />` and the per-workspace stack, sibling to (not inside) the absolute-positioned workspace divs. This is the first piece of global UI chrome to live in that slot — every other piece of vertical chrome today belongs to a single Workspace. Future global UI (e.g. an account/notifications strip) should go in the same slot rather than re-inventing a place for it. The strip is read-only — hovering a chip shows detail in a tooltip, but clicks do nothing; this keeps it a pure indicator and avoids a routing layer between counts and the things they count. Zero-count chips render dimmed rather than hidden so the layout is stable and the eye learns chip positions instead of re-scanning.

> **Update (2026-06-10):** the empty-state concession below — "no PR data until the user opens a Workspace" — was reversed. When the set of **Opened workspaces** is empty (zero workspaces activated this session), the **Pull Requests** section and these Overview bar chips now load account-wide PRs by running `gh search` from the user's home directory (`run_gh` falls back to `dirs::home_dir()` on an empty cwd). This does **not** reintroduce the rejected "dedicated global PR fetcher": it reuses the same `usePrStore` fetch path and its auth/error/cache handling, just with a home-dir cwd instead of a Workspace cwd. The only relaxation of the "all `gh` traffic goes through a cwd tied to a Workspace" pattern is the home-dir fallback for the account-wide (`-all`) searches, which are repo-independent anyway; the `-repo` views are never fetched in this state. Both PR sub-sections force their `-all` view while the Opened set is empty (the per-section repo/all preference is preserved and restored when a workspace reopens). See CONTEXT.md flagged ambiguities.

> **Update (2026-06-16):** the "strip is read-only — clicks do nothing" stance above was relaxed by one affordance. The Overview bar gained a single right-aligned button that opens the **Statistics overlay** (ADR-0018). "Read-only" is now scoped to mean it never *mutates* app or workspace state — it still carries exactly one *navigation* affordance (reveal a view), which is why "dashboard" was dropped from its glossary _Avoid_ list (that word now names the overlay it launches, not the bar). The button lives after the Pull-requests section via `margin-left:auto`; it is interactive (hover/active styling) precisely to distinguish it from the read-only count tiles.

The PR counts piggyback on the existing per-workspace PR fetch lifecycle instead of getting their own. `gh search prs --review-requested=@me` and `--author=@me` are scoped to the authenticated GitHub *user*, not the repo, so the cwd is inert for filtering — any workspace's fetch returns the same global data. The Overview bar therefore reads from `usePrStore`, with one wrinkle: the PR side panel has a per-section view toggle (`review-all` vs `review-repo`, `mine-all` vs `mine-repo`), and the chip must always show the `-all` count regardless of what the panel shows. So when the panel is in a `-repo` view, the workspace-activation fetch additionally requests the `-all` variant for the chip alone. Considered and rejected: a dedicated global PR fetcher with its own timer/focus lifecycle, independent of any workspace. Rejected because it would duplicate the panel's auth/error/cache handling and break the existing pattern that all `gh` traffic goes through a cwd tied to a Workspace; the duplication cost outweighed the slightly nicer empty-state behaviour (no PR data until the user opens a Workspace, which is acceptable because the bar is most useful once you're already working). The label "Opened" (not "Active") matters: **Active workspace** is a glossary singleton, so a plural "active" would silently collide.
