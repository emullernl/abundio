# Agent status hooks are provisioned into global agent config files

Abundio mirrors each Agent's lifecycle into its status indicator by registering hooks in that Agent's hook system. Hook payloads carry no Pane/PTY identity, so correlation rides on a per-PTY env var read by a small relay; and Agents load hooks only from global or per-project config. Redirecting each Agent's config home per-PTY would detach it from the user's auth and settings, so we instead merge Abundio's hook entries into the **global** agent config (`~/.claude/settings.json`, `~/.codex/hooks.json`, etc.).

Status hooks are **on by default**: the Settings toggle is opt-out, and a `persist` v2 migration also enables them for existing users who only ever saw the earlier off default. This means the relay is provisioned machine-wide on first launch without explicit user action, and the relay runs for every invocation of that Agent — not just inside Abundio. Accepted because the relay is a pure observer that exits immediately as a no-op when the Abundio PTY env var is absent and never alters the Agent's behaviour; Abundio removes only its own entries when the toggle is disabled; and the in-app toggle description discloses the global-config edit so it is not silent.

## Revisited 2026-06-05 — provisioning is no longer a toggle-only, restart-bound act

Originally, hook entries were (re)written only when the Settings toggle changed; a freshly-installed Agent therefore had no hooks until the user toggled off/on or restarted Abundio, and startup only refreshed the relay *scripts*, not the config entries. We broadened **Hook provisioning** to run at several moments, all still gated by the **Status Hooks setting** and now also by each Agent's own enable toggle:

1. **App startup**, once per process. A Rust-side `AtomicBool` guard makes provisioning run a single time however many **Windows** open, replacing the previous per-Window frontend `onRehydrateStorage` call that wrote the same global config files N times. The enabled flag still lives in the frontend and is pushed to Rust (mirroring the updater's auto-check pattern) — no Rust-side settings persistence was introduced.
2. **The Settings toggle** — the always-run path. `provision` now also takes the set of per-agent-enabled ids (see below).
3. **Toggling an individual Agent.** An Agent's own enable toggle (which already gates command detection) now also gates its hooks: toggling it off strips just that Agent's entries, toggling it on reinstalls them. `provision(enabled, enabledAgents)` re-syncs every supported Agent to its toggle in one call, so an Agent gets hooks only when the global setting AND its own toggle are on.
4. **The first time an Agent is launched** in a Pane, via `ensure_agent_hooks(agentId)`: Rust inspects only that Agent's config for the relay marker and registers just that Agent if missing. The LaunchPicker path *awaits* this before typing the command (so hooks fire the current session); manual-typed launches detected at `command_start` call it best-effort (the process has already read its config, so it only takes effect next run). Only enabled Agents reach this path — the picker lists only enabled Agents and detection skips disabled ones — so it never contradicts the per-agent gate.

**Relaxation of the no-litter rule.** ADR-0003 above states Abundio touches an Agent's config "only when it already has a config directory." That still holds for **startup** provisioning. It is **relaxed for the launch path only**: launching an Agent is explicit intent, so `ensure_agent_hooks` may *create* the Agent's config dir (and a minimal config) if absent — most CLIs create their config dir only on first run, so without this a brand-new Agent's first run would still get no hooks. Alternatives weighed: never create (rejected — defeats the first-run scenario this change targets) and create everywhere including startup (rejected — would scaffold dirs for Agents the user installed but never runs).

A read-only **Provisioning footprint** per Agent was added to Settings (config path, merged-vs-owned, hooked events, and a live status) so the global-config edits remain disclosed at the per-Agent level, extending the "not silent" property above.
