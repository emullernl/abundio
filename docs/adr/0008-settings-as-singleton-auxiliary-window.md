# Settings is a singleton auxiliary Window with payload-broadcast cross-window sync

Settings is its own OS-level Tauri Window — label `settings`, opened (or focused, if already open) via the File menu, Cmd+,, or the "Manage Profiles…" deep-link. Inside, it renders a dedicated `SettingsApp` root (not `App`) that mounts only the `SettingsPanel`. The window is auxiliary: it never claims a Profile in the per-window `ActiveProfileState` map, never appears in `windows.json`, and never counts toward the "last window closing quits the app" rule from ADR-0007. The predicate `window_management::is_profile_window_label` (true for everything *except* `settings`) is the single boundary used by lifecycle, persistence, and quit logic to distinguish profile-bound windows from auxiliary ones.

The earlier shape was a per-window React modal — every profile window mounted its own `<SettingsPanel open={...}>` overlay. That worked in single-window land but broke in multi-window land for two reasons. First, the menu-driven "Settings…" event routed through `emit_to_focused`, which falls back to a broadcast when the menu has focus and no window reports `is_focused() == true`; the modal then opened in every window simultaneously. Second, even with perfect focus detection, theme/font/agent changes inside the modal updated only *that* window's `settingsStore` — other windows kept their old values until their next launch. A singleton window is the right structural answer: there is one settings UI for the app, and any change there propagates to all live windows.

Cross-window settings sync uses **Tauri events with the changed data in the payload**, not the browser-native `storage` event. The natural-looking design — write to localStorage in the settings window, listen for `storage` events in profile windows, call `useSettingsStore.persist.rehydrate()` — turns out not to work on Tauri 2 macOS: each WKWebView has its own `WKWebsiteDataStore`, so localStorage is isolated per-window and `storage` events don't fire across them. The replacement: `SettingsApp` subscribes to its own zustand store, computes the persisted partial slice on every change, and emits a `settings-store-changed` Tauri event with that partial as payload; profile-window listeners receive the payload, write it into *their own* localStorage in the exact zustand-persist shape (`{state, version}`), and call `rehydrate()` to trigger `onRehydrateStorage` — which is the central hook that calls `applyTheme` (CSS variables), `setAllTerminalsTheme` (xterm canvases), and the font CSS-property setters. This shared-nothing replication pattern is robust against the per-WKWebView storage isolation, requires no Rust changes once the IPC is wired, and keeps each window's localStorage as a durable local copy.

Profile-delete semantics were also relaxed from the strict ADR-0007 rules. The original "forbid deleting a profile owned by another window" + "forbid deleting active profile when no auto-switch target exists" gates were necessary when delete originated from a profile window's settings modal — they prevented yanking a profile out from under another window's UI. With Settings as a separate window editing the *global* registry, the second rule is structurally unreachable (the settings window has no active profile), and the first rule is replaced by an explicit confirm dialog: "This profile is currently open in another window. Deleting it will close that window and permanently remove all of its workspaces, tabs, and saved layouts." On confirm, the Rust `profile_delete` command destroys the owning window first (synchronous `destroy()` rather than `close()` — the user already agreed), removes its entry from the ownership map, and then deletes the profile (which cascade-deletes its workspaces via the FK). The "at least one profile must exist" invariant is still enforced inside `ProfileStore::delete`; the last-remaining profile's delete button is disabled with a tooltip.

Window-label considerations made this work. Tauri 2 capability files (`src-tauri/capabilities/default.json`) gate permissions by window label. The settings window's label `settings` had to be added to the allowlist or `getCurrentWindow().close()`, `emit`/`listen`, and every other IPC silently failed. The native Quit menu also had to be replaced with a custom `MenuItem` (id `quit-app`) so quit could route through `on_menu_event` *before* windows started destroying — `RunEvent::ExitRequested` fires only after the last `Destroyed`, too late to snapshot `windows.json` cleanly. The settings window itself uses `WebviewWindowBuilder` with `title_bar_style(TitleBarStyle::Overlay)` and `hidden_title(true)` to match the profile windows' chrome, and the shared `Titlebar` React component accepts a `title` prop override so the settings window renders "Settings" instead of the profile-qualified title.

## Consequences

- `SettingsApp` is a parallel React root to `App` — both must register listeners for app-wide Tauri events independently (`profile-ownership-changed`, `profiles-changed`, `settings-store-changed`). There is no implicit propagation. A code-review heuristic: any `useEffect` containing `listen("…", …)` in `App.tsx` should be examined for whether it needs to also exist in `SettingsApp.tsx`.
- `SettingsApp` deliberately bypasses `profileStore.loadProfiles()` — that method has a reconciliation tail that pushes `setActiveProfileId(next)` to Rust, which would register the settings window as the owner of (typically) the first profile. The settings window must load profiles via `profilesApi.list()` + `setState({ profiles })` directly, never via `loadProfiles`. The `set_active_profile_id` IPC also rejects calls from non-profile-window labels as a backend defense in depth.
- Adding a new auxiliary window (a hypothetical "What's New" splash, an "About" dialog as a separate window, etc.) follows the same pattern: pick a stable singleton label, add it to the capabilities allowlist, exclude it from `is_profile_window_label`, and have it render a dedicated root in `main.tsx`. Every existing lifecycle/persistence filter automatically applies once the predicate is updated.
- Restoration on launch filters `windows.json` entries through `is_profile_window_label` defensively — if a pre-fix build left a `settings` entry in the file (from when the settings window briefly polluted the ownership map), the filter skips it and the file is overwritten cleanly on next quit. Users upgrading from a broken build don't need to manually delete `windows.json`.
- The payload-broadcast sync covers only the `settingsStore` persisted partial (theme, fonts, agents, etc.). Per-window state (sidebar collapsed, git panel open) explicitly does *not* sync — each window's `windowUiStore` is independent by design. If we add new globally-shared settings, they need to be in the `partialize` slice that `SettingsApp`'s subscriber broadcasts.
- Theme application is now a two-step "persist then rehydrate" cycle, not a direct `applyTheme()` call. Adding a new theme-dependent UI piece (a new CSS variable, a new component that reads `--accent`, etc.) Just Works as long as `applyTheme` writes the variable — `onRehydrateStorage` calls it on every sync. Visual side effects that *aren't* CSS-variable-driven (e.g. xterm canvas re-tinting via `setAllTerminalsTheme`) need to be added to `onRehydrateStorage` explicitly.
