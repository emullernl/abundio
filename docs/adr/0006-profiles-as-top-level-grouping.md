# Profiles are a top-level grouping over Workspaces, scoped narrowly to the workspace list

A **Profile** sits above the **Workspace** as a new top-level entity. Each Workspace belongs to exactly one Profile via a `profile_id` NOT NULL foreign key with `ON DELETE CASCADE`. A new `profiles` table holds `(id, name, position, created_at, updated_at)` — no color, no icon, no per-profile theme, no per-profile agents, no per-profile env vars, no per-profile GitHub identity. The migration creates one row named "Default" and backfills every existing Workspace's `profile_id` to it. The active Profile is persisted in the frontend `settingsStore` (localStorage `abundio-settings`), not in SQLite, because it is a UI-state singleton and follows the same lifecycle as `theme` / `fontSize`; if the persisted id points at a deleted Profile on load, the frontend falls back to the first Profile in position order.

The scope is deliberately narrow. The user's original framing implied a thicker bundle (theme, agents, GH identity, env vars) — closer to VS Code Profiles or browser profiles — and we explicitly rejected that for the initial cut. Putting GH identity per-profile alone would have required wrapping `gh` with per-call `GH_TOKEN` or `--user`, which is a non-trivial refactor of `gh_commands.rs` and the `usePrStore` aggregation, and was hard to justify before the grouping itself had been shipped and exercised. Per-profile theme/agents would have meant retro-fitting `settingsStore` into a per-Profile keyed map and re-skinning all xterm.js instances on switch. By holding the scope to "just a workspace list," we keep the migration small and the active-Profile transition cheap; the term "Profile" was kept (against the narrower fit of "Space" or "Group") explicitly so the scope can widen later without a rename and without invalidating muscle memory built up against the menu, palette, and status bar labels.

The Workspace ↔ Profile assignment is **locked at creation**. We considered adding a "Move to profile…" affordance and rejected it: workspaces carry tab layouts, PTY scrollback logs on disk under per-pane filenames, branch tracking state and file watchers, and moving a Workspace mid-session while preserving all of that is meaningful engineering effort for a marginal UX win. Users who realise a Workspace belongs in a different Profile delete it and recreate — the cost is one tab layout, which is what the user themselves did before having Profiles at all. We also considered allowing the same Workspace to appear in multiple Profiles (a join table) and rejected it because it re-introduces cross-Profile coupling that the "switching closes everything" rule is designed to eliminate.

Switching Profile closes all **Opened workspaces** in the previous Active profile — same code path as `closeWorkspace`, just iterated over every opened workspace in the outgoing Profile — gated by a confirm dialog when the outgoing Profile has any opened ones. We considered keeping Opened workspaces warm across Profile boundaries (the ADR-0002 "snappy switching" pattern, just one layer up) and rejected it: a Profile-A PTY that stays alive while the user is in Profile B would show up in the Overview bar's Agent aggregates, despite belonging to a Profile not currently in the sidebar. That coupling defeats half the reason for having Profiles. The pleasant side-effect of the close-on-switch rule is that every aggregation built on "Opened" (the Overview bar, `usePtyActivityStore`, `useWorkspaceGitStore`) needs zero awareness of Profiles — the set is empty for non-active Profiles by construction, so no filtering is required.

The Default profile is unprotected after migration. It can be renamed and even deleted, as long as another Profile exists; the only invariant is "at least one Profile must exist." A more rigid "Default is permanent" rule would force users into a profile they don't use. Deleting the *active* Profile auto-switches to the first remaining Profile (by position), so the user is never in a no-Profile state.

Three UI surfaces hold the Profile concept: the **StatusBar** (right side, next to the workspace name) renders the active Profile name as a read-only label — switching is never initiated from the status bar; the **native File menu** carries a `Switch Profile` submenu with each Profile as a checked entry plus a `Manage Profiles…` footer that opens the Settings panel scrolled to the Profiles section; and the **command palette** has a flat `Profiles` category with one `Switch to Profile: <name>` entry per non-active Profile, plus a `Manage Profiles…` action. The native menu must be rebuilt (`app.set_menu(build_menu(...))`) on every Profile create/rename/delete — Tauri's menu is constructed once at startup but `set_menu` is callable at any point; the IPC handlers in `commands.rs` for profile mutations emit a signal the setup callback listens for. Creating a Profile in Settings does **not** auto-switch to it — keeping the close-opened confirm dialog out of the Settings panel, where it would feel jarring.

## Consequences

- DB migration `008_add_profiles.sql` is irreversible without data loss: the `profile_id` column is NOT NULL, and the `profiles` row that owns existing Workspaces is required for any downgrade to put them back into a flat-list shape. Roll-forward only.
- The native menu rebuild is mandatory on Profile CRUD; forgetting it leaves stale entries that point at deleted Profiles. Tests for `profiles_*` commands should assert the menu was re-set.
- Switching Profile is a destructive operation in the sense that running agents die. The confirm dialog must be unmissable when any workspace is Opened; the rule "no confirm when nothing is opened" is the only quiet path.
- The active Profile id lives in localStorage, not SQLite. A user clearing localStorage (or running a fresh build with a wiped settings store) lands back on the first Profile by position rather than the one they used last — acceptable trade-off because the same is already true for `theme` and `fontSize`.
- Future scope expansion (per-profile theme, agents, GH identity, env vars) does not require renaming or rerouting the entity; only adding columns/sub-tables and wiring them into `settingsStore` / `gh_commands.rs`. The decision to keep the word "Profile" despite the current thin scope is what makes that expansion non-breaking.
- The Workspace lock means the only way to "move" a Workspace between Profiles is delete-and-recreate. If demand for in-place moves emerges, a `move_workspace` IPC command can be added without changing the schema (`UPDATE workspaces SET profile_id = ?`), but the PTY logs and pane state still need a story for that path; deferred.
