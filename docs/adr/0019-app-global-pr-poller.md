# GitHub PR data is fetched by one app-global poller via a single GraphQL call

Abundio fetched PR data **per Window** through five `gh` commands (`gh_status`, `gh_review_requests{,_all}`, `gh_my_prs{,_all}`), and each `-all` cycle ran `gh search prs` *plus* a second `gh api graphql` enrichment call (the search API omits `reviewDecision`/`statusCheckRollup`). In the default "All" view that is ~4 subprocesses every 60 s, multiplied by every open Window — enough traffic that GitHub began flagging it as **scraping** (secondary rate limits). We replace the whole path with a **single app-global background poller** (`pr_poller.rs`, modelled on `updater.rs`) that runs **one** `gh api graphql` query returning *both* lists — `review-requested:@me` and `author:@me` — each already carrying `reviewDecision` and `statusCheckRollup { state }`, then **broadcasts** the result to every Window via a `pr-state` event. Repo-vs-All is no longer two different commands; the poller always fetches the account-wide set and the frontend filters to the active repo **client-side** (matching a PR's `repository` against a new `git_libgit2::github_repo_slug(cwd)` helper that replaces the old per-workspace `hasRemote` probe).

This **directly reverses ADR-0005's** "Considered and rejected: a dedicated global PR fetcher with its own timer/focus lifecycle." Two things changed since that call. First, the driver: ADR-0005 weighed the global fetcher against merely "slightly nicer empty-state behaviour," whereas the motivation now is rate-limit sustainability — a correctness concern, not cosmetics. Second, the domain reinforces it: **GitHub identity is global, not per-Profile**, and the `-all` queries are account-scoped, so per-Window fetching was always N redundant fetches of identical data. ADR-0005's main objection — that a global fetcher would *duplicate* the panel's auth/error/cache handling — inverts under one owner: the poller is now the *single* place that handles all of it, so there is *less* total handling, not more.

The cadence is **focus-adaptive**: the user-configured interval (default 5 min, 1–30, set in a new Settings → GitHub section and disable-able via an "Off" switch) while any Window is frontmost, and a fixed 1 hour while backgrounded. A `WindowEvent::Focused(true)` wakes the poller for an immediate refresh, rate-limited by a min-gap equal to the focused interval (so the rule is simply "fetch at most once per interval while focused, anchored to when you actually return"). "Off" stops the timer and focus fetches but the manual **Refresh** button still does a one-shot fetch — the same auto-vs-manual split the updater uses for "Check now".

## Considered and rejected

- **Keep the per-Window fetch but slow it down / back off when collapsed** — does not remove the per-Window multiplier or the two-call enrichment, so it only postpones the scraping problem rather than fixing its shape.
- **`gh search prs` + client-side filter, drop enrichment** — would lose CI status and approval status entirely (the search API doesn't return them). Rejected in favour of one `gh api graphql` that carries both, so we keep the badges *and* drop to a single call.
- **Broadcast PR-change notifications to all Windows** — would surface N identical OS notifications when the app is backgrounded (every Window's store would diff and fire). The diff therefore runs **in Rust** and a `pr-changes` event is `emit_to` exactly one profile-bound Window (the updater's focused-else-any selection), which renders the notification with the profile-aware title and workspace-routing payload that can't move out of JS.

## Consequences

- `prStore` loses its per-workspace cache, the `-all` piggyback, the generation guards, and its entire notification-diff subscriber — it becomes a thin holder of two account-wide lists plus client-side filter selectors. `gh_commands.rs` loses all five commands and the enrichment machinery, keeping only the gh runner, auth cache, types, and `rollup_status`.
- A newly-opened Window has no data until the next poll (up to an hour when backgrounded), so the poller caches its last payload and exposes `pr_poller_snapshot()` for Windows to hydrate from on mount **without** triggering a gh call. Forcing a refresh on every window-open was rejected as a milder reincarnation of per-Window traffic.
- The empty-Opened-workspaces behaviour from ADR-0005's 2026-06-10 update (force `-all`, run from home dir) still holds, but its mechanism is now trivial: there is only ever one account-wide query (always from the home dir), and with no active repo there is simply nothing to filter to. CONTEXT.md's empty-state flagged-ambiguity entry is updated accordingly.
- One GraphQL `search` connection is capped at `first: 100` per list (parity with the old `--limit 100`); a list exceeding 100 is logged rather than silently truncated.
