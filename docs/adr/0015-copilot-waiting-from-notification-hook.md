# Drive Copilot's Waiting from the `notification` hook's `permission_prompt`, not `permissionRequest`

Copilot fires `permissionRequest` for every permission-gated tool (edits/writes; read-kind tools like `glob`/`view` short-circuit it) **even when auto-approved**, in the observed order `preToolUse → permissionRequest → postToolUse` (confirmed from captured `[abundio:hook]` logs — this contradicts GitHub's published docs, which put `permissionRequest` first). The only "tool finished/unblocked" signal, `postToolUse`, arrives *after* the tool runs. So `permissionRequest` alone can't tell a genuine block from autopilot at request time, and mapping it straight to **Waiting** flickered the sky-blue dot and fired a "needs your input" notification for every permission-gated tool — constant spam during edit-heavy autopilot in a background pane.

Copilot's `notification` hook exposes a `notification_type`, and a genuine permission prompt arrives as `notification_type: "permission_prompt"` — observed to fire **only** on real prompts, not auto-approved tools. We drive **Waiting** from that instead: the `notification` hook is provisioned with `matcher: "permission_prompt"` (Copilot filters at source — anchored `^(?:permission_prompt)$`), so the only `notification` events that reach Abundio are real prompts, and we map `notification → Waiting` directly. This removes `permissionRequest`, `postToolUse`, and `postToolUseFailure` from provisioning entirely.

The two prompt-tools that emit no `notification` — `exit_plan_mode` (plan review) and `ask_user` (multiple-choice) — keep their immediate-Waiting via a `preToolUse` hook whose `matcher` is scoped to just those tool names (`^(?:exit_plan_mode|ask_user)$`), so `preToolUse` no longer fires for every tool. A freshly-set Waiting dot is held against the permission prompt's *own render output* by a guard in `recordOutput` (agent-mode Waiting is overridden only by a keystroke or the next hook — the invariant `markIdle` already documents but `recordOutput` previously violated). It clears on the user's answer keystroke (digit/Enter → Working, ESC → Idle) or `agentStop → Ready`.

**Amendment (PR #140).** A deliberate left-click on the terminal screen is a third clearing path (Waiting → Idle), added later on the reasoning that engaging with the pane is equivalent to the ESC keystroke. So the invariant stated above — *agent-mode Waiting is overridden only by a keystroke or the next hook* — is no longer literally true; a click overrides it too. Two consequences to know about:

- A pane whose prompt you clicked into but did not answer reads **Idle** while the prompt is still live and blocking. Nothing repaints it: `reduceOutput` short-circuits on `hookDriven` and `reduceTick` only acts on `working`, so it stays green until you answer or `agentStop` arrives. Reading the prompt before answering is the most natural reason to click, so this is not rare.
- A click is nonetheless *not* an answer, which is why the `click` status event runs `clearWaiting` **before** `clearError`: a **Mid-turn failure** restored to Waiting must survive the click, because the Agent really is still blocked (ADR-0026).

## Considered alternatives

- **A 1500ms output-quiet debounce on `permissionRequest`.** Prototyped (and briefly committed on this branch before being reverted): a tool's `permissionRequest` started a 1500ms FIFO timer cancelled by `postToolUse`; if it elapsed with the pane output-quiet, the tool was treated as genuinely blocked. Rejected once `notification`'s `permission_prompt` turned out to be a clean genuine-prompt signal — the debounce (per-tool gates, timers, an output-quiet heuristic, plus known false-confirm residuals for silent long-running tools) was all machinery to *reconstruct* the signal Copilot now hands us directly.
- **Filter `notification_type` in the frontend (no provisioning matcher).** Rejected: every notification would still POST to the loopback server and get logged per-tool — the transport-layer version of the overload. The matcher filters at source and keeps `mapHookEvent` dumb (`notification` *is* Waiting, no payload parsing). Risk: a wrong matcher fires **never** (the codebase deliberately avoided a matcher for Gemini's undocumented permission token for exactly this reason) — mitigated by verifying the relay fires once with the matcher in place.
- **Drop `exit_plan_mode`/`ask_user` entirely.** Rejected: a silent regression to amber Working for plan/question prompts. A `toolName`-scoped `preToolUse` matcher preserves them at zero per-tool traffic.
- **Keep `postToolUse`/`postToolUseFailure → Working` as a clearing backstop.** Rejected: they fire for *every* tool (a per-tool POST + ~8 KiB log line each). The keystroke handler (Copilot prompts answer with digit/Enter), `agentStop`, and the `recordOutput` guard cover clearing without them.

## Known residuals

- **Load-bearing assumption: `permission_prompt` fires only on genuine prompts.** `github/copilot-cli#2586` (filed 2026-04-08, open) reports the `notification` hook firing with `notification_type: "permission_prompt"` for *every* tool execution in interactive mode, even already-approved ones. We rely on the observed clean behaviour for the current Copilot version. If Copilot regresses, per-tool Waiting + notification spam returns — the fix is to re-introduce a debounce (see the rejected alternative above) or find a payload discriminator (e.g. `title`/`message`). **This ADR is where to look.**
- **Possible double notification.** The `notification` hook fires *because* the CLI emits a system notification, so Copilot may post its own OS notification alongside Abundio's away-gated one. Abundio cannot suppress Copilot's; disable it in Copilot's notification settings if doubled. Abundio's is the better one (only when the pane is off-screen, and clickable to the pane).
- **Non-digit/non-Enter approval keys.** Answering a prompt with a key the keystroke handler doesn't recognise (e.g. `y`) leaves the dot Waiting until `agentStop`. Low risk — Copilot's prompts are answered with a digit or Enter.
- **`exit_plan_mode` tool name.** Copilot's documented tool-name list includes `ask_user` but not `exit_plan_mode`; the scoped matcher is harmless if `exit_plan_mode` never matches.
