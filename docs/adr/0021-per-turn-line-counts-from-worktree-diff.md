# Per-Turn line counts from a working-tree diff

ADR-0018 attributed each **Turn**'s lines as a **net-vs-base-branch** git delta — additions/deletions vs the base branch, sampled at Turn start and end, with the difference stored. In practice that recorded **+0 −0** for most *edit* Turns: `Math.max(0, …)` floored every net-negative Turn (reverts, cleanups, refactor-downs) to zero, and — more fundamentally — re-editing lines a previous Turn had already diverged from base leaves the vs-base total unchanged, so ordinary iterative agent work read as zero. The metric measured *movement of the cumulative vs-base total*, which is blind to intra-Turn churn.

We now compute each Turn's lines as a **per-Turn working-tree diff**: snapshot the Workspace's working tree to a git tree object at Turn start and at Turn end, then `diff_tree_to_tree` the two snapshots and use its insertions/deletions/files_changed as the Turn's counts. The snapshot builds an *in-memory* index seeded from HEAD, overlays the whole worktree with `add_all(["."])` (tracked edits + non-ignored untracked files + deletions, respecting `.gitignore`), and `write_tree_to`s it — **without ever calling `index.write()`, so the user's on-disk staging area is never touched** — the invariant being that Abundio never writes the index as a *side effect* of telemetry, polling or rendering (ADR-0029 later adds `git add` as the one explicit, user-initiated writer); only loose tree/blob objects reach the ODB (content-addressed, deduplicated, reaped by `git gc`). This measures the Turn's actual **net effect on the files** rather than its movement of the vs-base total, so reverts now count as deletions and re-edits of earlier-Turn code count as real churn.

## Why this shape

This is deliberately a *third* option, not the one ADR-0018 anticipated. 0018 framed the future as "approximate-but-universal (net-vs-base) now, precise-but-per-agent (parse `PostToolUse` payloads) later." The working-tree diff keeps the **universal, pure-libgit2, agent-agnostic** property of the original (identical for all six Agents, no per-Agent hook parsing) while fixing accuracy — so we get most of the precision benefit without the per-Agent fragility, and the per-Agent path remains available later if exact keystroke-level churn (including within-Turn redos) is ever wanted.

## Consequences

- **Accepted approximations:** within-Turn redos collapse to net (a line written then rewritten in one Turn counts once); a manual/external edit made after the prompt is submitted, or a brief **start-snapshot race** (edits landing between the turn-start hook firing and the async snapshot completing), can be mis-attributed. The metric stays labelled approximate.
- **Cost:** two snapshots per Turn (begin + finalize). Each is a working-tree stat-walk — a `git status`-class scan proportional to the **number of non-ignored files** in the worktree, not to the volume of uncommitted changes — plus hashing of only the changed/new files (libgit2's stat cache skips unchanged tracked files), and loose-object writes to the repo ODB. Equivalent to what `git add -A` + `git write-tree` already do, runs on a blocking thread (comparable to `compute_status_fingerprint_sync`), GC'd normally. On a very large repo this is a full stat-walk twice per Turn — acceptable but worth noting for heavy-turn workflows.
- **Schema unchanged.** `lines_added` / `lines_deleted` / `files_changed` now hold the churn; the vestigial `git_*_start/end` provenance columns are left NULL (the finalize-time net-vs-base `fetchBundle` is dropped — it was only there to re-derive the old metric). No migration.
- **Overlap unchanged.** Two Turns overlapping in one Workspace still record NULL ("unmeasured") — a shared working tree can't be split by author. Non-git Workspaces and unavailable start snapshots are likewise NULL.
- **Whole-repo, not folder-scoped.** The snapshot/diff covers the whole enclosing repo, so two *plain* Workspaces that are different subdirectories of the **same** repo (not separate worktrees) can cross-attribute concurrent edits — the `workspaceId`-keyed overlap guard misses it. This is not a regression (the old net-vs-base totals were whole-repo too) and is uncommon (worktree-set Workspaces each have their own workdir, per ADR-0017). Future refinement if shared-repo subdir Workspaces become common: scope the tree diff with a pathspec = the Workspace's path relative to the repo root (`"."` for root/worktree Workspaces, a no-op).
- **New files = `git add -A` semantics.** A file the Agent creates during a Turn is counted as additions from the moment it exists — even untracked, before any `git add` — because `add_all(["."])` folds untracked, non-ignored files (recursively) into the end snapshot; if it's later staged or committed within the Turn it stays counted. `.gitignore`d files are excluded (generated/vendored output isn't agent productivity); true line counts with no size cap (binaries count as 1 file / 0 lines). This supersedes the old cached-status `count_untracked_additions` path (per-file 1 MiB cap, non-recursive), which the new metric no longer uses.
- **Renames** are counted as delete+add (no `find_similar` rename detection) — parity with the prior metric, noted as a known approximation.
- The Statistics overlay's "Net lines" card becomes **"Lines changed"** ("changed during turns"); a genuine no-op Turn now correctly reads `+0 −0`, distinct from `unmeasured`.
