# Release notes come from GitHub Releases and are rendered in-app

Abundio's **Release notes** have only ever existed as the Markdown body of a published GitHub Release, and the app only ever linked out to them — the update prompt and the Settings → Updates section both offered "View release notes ↗" and nothing more. We now render them in the app: the **Updates section** shows the running version's notes plus every newer release's, and a **What's new card** shows the running version's notes after an upgrade. There is deliberately **no `CHANGELOG` in the repository**; the GitHub Release body stays the single source of truth, so notes are authored in exactly one place and a typo can be fixed after the fact without shipping a build.

Fetching is a Rust `#[tauri::command]` (`updater_release_notes`), like every other network call here — the updater check and the `gh` PR poller. One `GET /releases?per_page=30`, newest first, prereleases dropped because `build.yml` sets `prerelease: false` and the updater resolves `releases/latest`, which would never offer them. Drafts need no filtering at all: the unauthenticated API does not return them, which reproduces ADR-0014's rule that clicking *Publish* is the gate. The response is cached app-globally in `UpdaterState` for an hour, matching GitHub's unauthenticated 60-requests-per-hour budget.

Rust returns the raw list and stops there. Deciding *which* releases to show and under which heading is presentation, so it lives in a pure `selectReleaseNotes(current, releases)` in TypeScript, tested in Vitest beside the component states it drives. It has three cases, and the two unusual ones are the point: **ahead** (a development build running a version newer than anything published — the daily state while working on Abundio) must not render an empty page, and **behind** (an install so stale that its version fell off the single fetched page) must not silently drop the anchor. Both fall back to rendering everything fetched and change only the heading.

## Considered and rejected

- **A `CHANGELOG.md` embedded at build time.** Works offline, no network, no rate limit. Rejected because it forks authoring into two places that then drift, and it can never describe a version newer than the binary — which is exactly the version the update prompt is offering.
- **Per-tag point lookups** (`/releases/tags/vX`) for the current and new versions only. Two cheap requests, no semver comparison. Rejected once we decided a user several versions behind should see every release they skipped, which a point lookup cannot express.
- **Paginating until the installed version is found.** Complete history in every case, at several sequential round-trips against a 60/hour budget, and it still needs a cap — and therefore the same fallback — anyway.
- **Rendering notes inside the update prompt card.** It is a 320px notification whose job is Install / Later / Skip; an unbounded Markdown body turns a glance into a read.
- **A blocking modal for the What's new card.** Rejected for the reason ADR-0014 refused auto-relaunch: nothing interrupts live **PTY**s and **Agent** turns.

## Consequences

- **An offline user cannot read their own version's notes at all.** Nothing is cached on disk, so a cold start without network shows "Couldn't load release notes" and a link. Accepted as the price of a single authoring surface; persisting the last successful fetch would fix it at the cost of a new on-disk state file and stale content with no tell.
- **Markdown from the network enters the webview origin.** `@uiw/react-markdown-preview` bakes in `rehype-raw` and ships no sanitizer, so the shared `markdownSanitizeSchema` is load-bearing here in a way it is not for a local file the user opened deliberately. Links are routed through `plugin-shell`'s `open()` — a plain `<a>` click would navigate the whole app away, and there is no router to come back from.
- **GitHub's shorthand does not survive the API.** `body` is raw Markdown, so `#123`, `@mentions` and commit SHAs arrive as literal text. We linkify PR references only, because that is what the release-notes style actually uses; mentions and SHAs stay plain rather than buying three false-positive guards for content we do not write.
- **The What's new card cannot use `localStorage`.** It is per-webview on macOS, so every open **Window** would keep its own "last seen" copy and each would show its own card. `last_seen_version` therefore lives in the (previously unused) `settings` key-value table from `001_init.sql` — no migration, and the database is already epoch-versioned — and the card is emitted via `emit_to_focused`, the same mechanism the update prompt uses.
- **The card repeats until it is dismissed.** `last_seen_version` advances on dismissal, not on display, so quitting without touching the card — or never seeing it, because `emit_to_focused_profile_window` picked a Window the user was not looking at — brings it back next launch. Guaranteed delivery over guaranteed-once, for content that is shown at most once per upgrade anyway.
- **The version is marked seen only once notes were actually fetched.** An offline launch shows no card and leaves the flag alone, so the card turns up on a later launch instead of being silently consumed. The exception is a fetch that succeeds and finds no published release: that is an answer, not a failure, so it marks seen — otherwise a development build would re-fetch on every launch forever.
- **reqwest is built with `rustls-no-provider`**, matching what tauri-plugin-updater already resolves so no second TLS stack (and no aws-lc-rs/cmake build) is pulled in. That feature does what it says: a crypto provider being *compiled in* is not one being *installed*, and `Client::build()` panics with "No provider set" without it — which took down the tokio worker and left the Settings page on "Loading…" forever, because the command never replied. `ensure_crypto_provider()` installs rustls' ring provider once, tolerating another component having got there first. A fixture-based test could not have caught this, since the panic was in building the client rather than in anything parsed; `live_github_release_notes_fetch` (ignored by default) is the test that does.
- **Semver comparison now exists on both sides** — Rust for the What's new gate, TypeScript for anchoring. A three-integer compare over a format `scripts/release.sh` already enforces, duplicated deliberately rather than adding an IPC round-trip for it.
