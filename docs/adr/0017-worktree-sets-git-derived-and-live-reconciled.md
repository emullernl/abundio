# Worktree sets are git-derived and the workspace list live-reconciles with on-disk worktrees

A **Worktree set** — the visually-distinct cluster of Workspaces that are git worktrees of one repository — is **not** a stored entity. There is no `worktree_group_id` column, no `is_primary` flag, no migration. Membership is recomputed from git on every relevant tick: two Workspaces belong to the same set iff their folders resolve to worktrees sharing one `git_common_dir`, and the **Primary worktree** is whichever member is the repository's *main* worktree (libgit2's `Repository::worktrees()` lists only the *linked* trees, so the primary is detected as "the member whose folder is the main worktree", not by enumeration). This mirrors how branch names are already handled (`current_branch_only` fetched live, `lastBranch` kept only as a cosmetic first-paint cache) — git, i.e. the filesystem, is the single source of truth for facts about the filesystem. We rejected a stored `repo_group_key` + `is_primary_worktree` pair: it buys offline grouping and stable ordering, but it **drifts** the instant a worktree is added or removed outside the app, and would need reconciliation logic anyway — the same logic we'd need for live-sync, so the stored columns earn nothing but a migration and a second source of truth to keep honest.

Grouping is derived, but ordering still rides on the existing persisted `position` integer — we did not throw it away. The render layer imposes two constraints *on top of* `position`: set members render contiguous, and the primary renders first. A set sorts among the other rows by its primary's `position`; within a set the linked worktrees order by their own `position` (new worktrees append, so this is creation order). Consequently a **set is atomic under drag-reorder**: grabbing any member moves the whole block, and a member cannot be torn out — tearing out is meaningless when grouping is derived (the member would snap back on next regroup, since it is still the same repo on disk). The *only* way to split a set is to change git reality (Remove worktree). No within-set manual reordering ships in v1; it is low-value and would grow a second mode in the already-intricate `WorkspaceList` drag code.

The list **live-reconciles with disk in both directions.** Per *distinct repository* among a Window's active-Profile git workspaces, a watcher observes that repo's worktree admin area (`.git/worktrees/`) and the worktree folders; one watcher per repo, not per workspace, debounced because fs events are bursty. Reconciliation is **per-Window/Profile** — a repo open in two Profiles reconciles independently in each, consistent with every other per-Window invariant. **Auto-add is eager**: when a new worktree of repo R appears on disk and R already has at least one workspace in this Profile, the new worktree is added as an unopened, basename-named Workspace — *including the bootstrap case*, where a lone standalone git Workspace becomes a Primary worktree the moment a sibling is `git worktree add`-ed in any terminal. We rejected restricting auto-add to repos that are already sets: "live CLI-sync" most naturally means "the sidebar reflects `git worktree` commands," and the bootstrap path is exactly the one a user reaches for.

**Auto-remove is deliberately conservative**, because removing a worktree's entry cascade-deletes that Workspace's tabs, pane layout, notes, and env vars (FK cascade) — real, unrecoverable state. The trigger is therefore **git-confirmed removal** (the worktree no longer appears in the repo's worktree list), not "the folder isn't there this instant." A folder can be absent for benign reasons — an unmounted drive, a move in progress, an `rm -rf` about to be `git worktree prune`d — and in that ambiguous "missing but git still lists it" state the entry **degrades to a stale render** (no branch chip, no group) rather than being deleted. We rejected the aggressive "any folder disappearance deletes the entry": it turns a transient mount blip into silent loss of a workspace's layout and notes. The common path — a real `git worktree remove` — still makes the entry vanish within a debounce tick, which is what "live-sync" was asked for.

Two flows mutate git directly. **Add worktree** (Primary-only, also offered on a standalone main-worktree Workspace to bootstrap a set) takes a branch name and a folder. Because libgit2's `git_worktree_add` requires an *existing* reference, a new branch is created first (forked from the primary's current HEAD) and the worktree is then added pointing at it; an existing local branch is checked out directly (erroring if already checked out elsewhere — git forbids one branch in two trees); an `origin/<name>`-only branch gets a local tracking branch first. The default folder `../<repo>.worktrees/<branch-with-slashes-as-dashes>` resolves relative to the primary root. **Remove worktree** (Linked-only) prunes via `Worktree::prune` with `working_tree(true)`, after killing the workspace's PTYs and tearing it down; the **branch is kept** (matching `git worktree remove` semantics), so only uncommitted/untracked changes are at risk — which the single, dirty-aware confirm dialog escalates its wording to name.

## Consequences

- No migration and no schema change for the grouping itself — the feature is additive over the existing `workspaces`/`tabs` tables. Should stored grouping ever be wanted (e.g. for offline ordering), it can be added later as a denormalized cache without invalidating the derive-from-git source of truth.
- The persisted workspace store now **mutates from a file watcher** — a genuine surprise in a codebase where Workspaces are user-authored everywhere else. Any future reader auditing "who writes to the `workspaces` table" must account for the reconciler, not just the IPC command handlers in `commands.rs`.
- One fs watcher per distinct repository in the active Profile. A Profile with many distinct git repos pays a watcher each; the per-repo (not per-workspace) granularity bounds this, and watchers are scoped to the active Profile only.
- Auto-remove cascade-deletes layout/notes/env for the removed Workspace. The git-confirmed gate is the safety rail; weakening it to folder-absence would make a transient unmount destructive. Tests for the reconciler must cover the "folder missing but git still lists it" branch and assert it does **not** delete.
- The picked folder **snaps to its worktree root** on create when it belongs to a multi-worktree repo (a behavior change for the rare case of picking a subdirectory), because primary-detection and dedup both key off worktree roots.
- Degenerate shapes fall out of the rules without special cases: a **primary-less set** (primary entry deleted via Close Workspace while linked entries remain) renders its members as ordinary standalone workspaces, since set chrome requires a present primary anchor; a **bare repo** (no main worktree) likewise has no primary and renders flat, with Add worktree unavailable until a main-worktree workspace exists. Locked worktrees are honored on remove — a lock blocks prune unless explicitly forced.
- Add worktree depends on the create-branch-then-add sequence, not a single libgit2 call; a failure between the two steps (branch created, worktree add fails) must clean up the orphaned branch or surface it, rather than leaving a dangling new branch.
