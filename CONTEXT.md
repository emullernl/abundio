# Abundio

GPU-accelerated terminal multiplexer. The user opens one or more application Windows; each Window shows one Profile; each Profile owns a set of Workspaces; each Workspace runs its own pane layout and PTY processes.

## Language

**Window**: A single OS-level application window (Tauri `WebviewWindow`). Windows come in two kinds:
- **Profile-bound window**: owns exactly one **Profile** (one-to-one, exclusive — a Profile is open in at most one such Window at a time). Created via File → New Window with Profile. Appears in `windows.json` for restoration across launches and counts toward the "last-window-closing quits the app" rule. Labels follow the pattern `main` (the first window) or `window-<uuid>` (additional windows).
- **Auxiliary window**: serves a global purpose unrelated to any single Profile. Currently only the **Settings window**. Does not own a Profile, is not persisted in `windows.json`, and does not count toward the quit rule. Uses a stable singleton label (`settings`).

The label is the stable identifier across launches — both Abundio's own `windows.json` and `tauri-plugin-window-state` key per-window data by it.
_Avoid_: viewport, app instance, frame; do **not** use "window" to mean a **Pane** (see Pane).

**Settings window**: The singleton auxiliary **Window** labelled `settings`. Opens (or focuses if already open) via File menu, Cmd+,, or the "Manage Profiles…" deep-link; with no section requested it lands on Theme. Edits the *global* profile registry — has no active Profile of its own. Every global setting changed here propagates live to all open Profile-bound windows via a Tauri event broadcast, except a small denied set — the drag-derived sidebar widths, the activity byte threshold, and the last-opened dev environment breadcrumb — which are global but too noisy to broadcast. The propagation is bidirectional: a command-palette toggle in a Profile window reaches Settings too. See ADR-0008.
_Avoid_: preferences window, options dialog.

**Settings section**: One leaf page of the **Settings window**, and the unit its deep-link addresses. Nine of them, presented under three non-clickable group captions: *Appearance* (**Theme**, **Fonts**), *Panes* (**Terminal**, **Editor**), *Application* (**Agents**, **Prompt actions**, **Profiles**, **GitHub**, **Updates**). The section ids cross the Rust→JS boundary as `open_settings_window { section }` — encoded in the window URL on a cold open, emitted as a `settings-set-section` event when the window is already open — so they are vocabulary, not implementation detail. **Group captions are not addressable**: there is no `appearance` section. Ids from before the regroup (`terminal-font`, `ui-font`, `shell`) still resolve, in `lib/settingsSections.ts`.
_Avoid_: settings tab, settings panel (see the **Workspace settings** entry).

**Settings ▸ Editor**: A UI label, not a domain term — the section configures both the **file pane** (wrap long lines) and the **preview pane** (whether opening a markdown file spawns one). It is named for what users call Monaco, and is deliberately not folded into Appearance: auto-opening a preview is layout behaviour, not look. The **Preview color mode** stays on the preview's title bar per ADR-0013; the section points at it rather than duplicating it.

**Profile**: A top-level grouping of Workspaces — a named bundle the user uses to organize unrelated bodies of work (e.g. "Work", "Personal"). Each **Workspace** belongs to exactly one Profile and cannot be moved between Profiles after creation. The only per-Profile data today is the Workspace list; appearance, custom agents and GitHub identity remain global, and environment variables are per-**Workspace** (see Environment Bundle). Scope is intentionally narrow so the term may broaden later. A Profile is bound to at most one **Window** at any moment.
_Avoid_: space, group, namespace, context

**Active profile**: The single Profile currently shown in a given Window. Per-Window singleton — Window A's active profile is independent of Window B's, but a Profile cannot be active in two Windows at the same time. Switching Profile closes every Opened workspace in the previous Active profile of *that Window* (with a confirm dialog when any are open). Persisted across restarts per-Window.
_Avoid_: current profile, selected profile, focused profile

**Default profile**: The Profile created at migration time to host pre-existing Workspaces. After migration it has no permanent specialness: it can be renamed, and it can be deleted as long as another Profile exists. The system invariant is "at least one Profile must always exist" — not "the Default must exist".
_Avoid_: primary profile, root profile, main profile

**Workspace**: A folder-bound container with its own pane layout, tabs, and PTY processes. Belongs to exactly one **Profile**.
_Avoid_: project, folder

**Active workspace**: The single Workspace currently selected and visible to the user *within a Window*. Per-Window singleton (`useWorkspaceStore.activeWorkspaceId` — each Window has its own JS context and so its own store instance).
_Avoid_: selected workspace, current workspace, focused workspace

**Opened workspace**: A Workspace the user has activated at least once *in its Window* and has not closed. Tracked per-Window by `usePtyActivityStore.openedWorkspaceIds`. PTY processes and file watchers stay alive for these even when not the Active workspace.
_Avoid_: loaded workspace, mounted workspace

**Background workspace**: An Opened workspace that is not currently the Active workspace. Not a separate state — derived as `openedWorkspaceIds \ {activeWorkspaceId}`.

**Environment Bundle**: A named, ordered set of environment variables owned by a **Workspace** (e.g. `default`, `production`). At most one Bundle per Workspace is the **Injected bundle**; the rest are **On-demand bundles**, and a Workspace may have no Injected bundle at all. Values are encrypted at rest under a single **Master key**; variable *names* are stored in plaintext so the settings list renders without touching the credential store. A Workspace's first variable creates a Bundle named `default` automatically. See ADR-0024.
_Avoid_: env group, env set, env profile (collides with **Profile**), secret store, vault

**Injected bundle**: The Bundle — at most one per Workspace, possibly none — whose variables are placed into the environment of every PTY the Workspace spawns. Set with the green injection toggle beside the bundle row in workspace settings — turning it off leaves every Bundle on-demand — and named by a read-only green pill in the status bar. Changing it affects only *future* terminals — existing PTYs keep the environment they were spawned with until explicitly restarted.
_Avoid_: active bundle, default bundle (`default` is a name, not a role — any Bundle can be the Injected bundle)

**On-demand bundle**: A Bundle that never enters any process environment on its own. Read only through the `abundio-env` helper from inside a pane, typically `abundio-env run <bundle> -- <command>`. This is where credentials that should not be visible to every terminal in the Workspace live.
_Avoid_: manual bundle, inactive bundle

**Master key**: The single 32-byte AES-256-GCM key, held in the OS credential store, that seals every environment variable value. One key per user per machine, not per Workspace or per Bundle. When it cannot be read, environment variables are simply unavailable — terminals still open.
_Avoid_: encryption key, secret key, passphrase

**Shadow variable**: An `ABUNDIO_ENV__<NAME>` copy of an injected variable, set at spawn and re-exported by Abundio's wrapper rc *after* the user's own rc has been sourced, then unset. Its only purpose is precedence: without it an `export` in `.zshrc` would silently beat the Workspace's value. Never visible in a settled shell.
_Avoid_: temp variable, mirror variable

**Inherited variable**: A variable a **Linked worktree** sees because it exists in its **Primary worktree**'s Bundle of the same name. Not a copy — it is read through at spawn time, so editing it in the primary updates every linked worktree. Saving an inherited variable in a linked worktree creates an **Override**: an own row that shadows the inherited one by name, leaving the primary untouched.
_Avoid_: shared variable, parent variable

**Worktree set**: A group of Workspaces that are git worktrees of the same repository — one underlying repository, different branches checked out into different folders, each folder its own Workspace. Rendered as a single visually-distinct cluster in the **Left sidebar**; never a separate stored entity and never a **Profile**. Derived live from git, not persisted: two Workspaces belong to the same set iff their folders are worktrees of the same repository. A repository present only through its main worktree forms no set — the cluster chrome appears only once two or more worktrees of one repository exist as Workspaces. Within a set the **Primary worktree** is always rendered first, followed by the **Linked worktrees**.
_Avoid_: worktree group, repo group (collides with **Profile**'s sense of "group"), worktree cluster.

**Primary worktree**: The Workspace bound to a repository's *main* working tree (git's "main worktree"). Exactly one per **Worktree set**, always rendered first within it. **Add worktree** is offered here — and equally on a standalone git Workspace whose folder is a main worktree but has no set yet; that Workspace simply isn't *called* a Primary worktree until its first linked worktree exists.
_Avoid_: main worktree (git-side synonym, ok colloquially), root worktree.

**Linked worktree**: A non-primary Workspace in a **Worktree set** — a working tree git links to the repository's main one (git's own term for the non-main worktrees). The only Workspace on which **Remove worktree** is offered; removing it deletes that worktree's folder from disk.
_Avoid_: secondary worktree, child worktree.

**Folded set**: A **Worktree set** whose **Linked worktree** rows are hidden in the **Left sidebar**, leaving only its **Primary worktree** row — which then carries a **hidden rollup**. A per-**Window** view preference, kept in `windowUiStore` keyed by the set's git-derived group key, so two Windows showing the same repository can disagree. Deliberately *not* called "collapsed": that word already means the Left sidebar itself is narrow (`sidebarCollapsed` / `CollapsedStrip`), and folding is honoured in both sidebar widths. A folded set never hides the **Active workspace** — activating a hidden member unfolds the set.
_Avoid_: collapsed set (collides with the narrow sidebar), closed set, hidden worktrees.

**Hidden rollup**: The status a **Folded set**'s Primary row shows *on behalf of the members it is hiding* — an **Agent rollup** and a **Terminal rollup** taken across all of them, drawn at the row's right end as one **Status composite** followed by the count of hidden members, hovering to a breakdown summed over them. When at least one hidden member is a **Dirty workspace**, the rollup also carries a **Dirty marker** (its hollow-ring form), and its member tooltip says which members are dirty — so folding a set never hides uncommitted work. Hidden members only, as ever: the Primary's own dirtiness is the bar down its row's edge. The narrow sidebar has no room for a second **Status composite**, so there the Hidden rollup is a `+N` count label instead: neutral grey for Idle and Working, tinted with the members' most urgent status only when that is **Error**, **Waiting** or **Ready** — the same set that earns an OS notification, so a colour there always means "something in here wants you" and never "N things are running". The count's own tooltip still gives the per-member breakdown. It covers the hidden **Linked worktrees** only, never the Primary itself, whose own status icon keeps its ordinary meaning in the row's left slot — so the icon beside a name always describes the Workspace that row activates. Folding changes what is *drawn*; it never changes what is *notified* (OS notifications from a hidden worktree fire exactly as they do unfolded) and never suppresses the underlying activity tracking.
_Avoid_: set status, aggregate status, group dot (the per-Pane indicator is a **status icon**, never a "dot").

**Workspace settings**: A per-Workspace dialog opened from the **Left sidebar** context menu (`Workspace settings…`). Hosts the Workspace rename and — only for **main-worktree** Workspaces (a **Primary worktree**, or a standalone main worktree) — the **Worktree setup commands** box; Linked worktrees and non-git Workspaces see the rename field alone. A plain in-window dialog, *not* the **Settings window** (which is a global, OS-level auxiliary Window editing the profile registry); Workspace settings edits one Workspace's own row.
_Avoid_: preferences, workspace config, settings panel (collides with **Settings window**).

**Worktree setup commands**: An ordered list of shell commands stored on a **main-worktree** Workspace's row and run in a newly created worktree's focal terminal immediately after an in-app **Add worktree** — and only then. A worktree created via the CLI and surfaced by live-sync is added unopened and runs nothing. The commands are sent as literal shell input (one line per command, the shell serializing them), ahead of any Agent chosen in the Add worktree dialog. Not a git "hook" and unrelated to **Agent hooks** or **Hook provisioning**.
_Avoid_: worktree hook, setup hook, post-create hook, init script.

**Pane**: A leaf slot within a Workspace tab. Panes form a recursive binary split tree (`PaneNode`). A Pane is one of: a **terminal pane** (holds a PTY), a **file pane** (holds an open file), or a **preview pane** (renders another pane's content).
_Avoid_: panel, window, split

**Mouse-reporting pane**: A **terminal pane** whose foreground program has asked to receive the mouse itself (DECSET 9/1000/1002/1003) and been allowed to. Possible only where the pane is not blocking — see **Mouse-blocked pane**, which is the default. In such a pane the mouse belongs to the program, not to Abundio: plain click-drag no longer selects text, because xterm hands its selection service over for the duration, and the **right button reaches the program** rather than opening the pane context menu. One gesture is reserved for the user regardless — **modifier-drag selects**, Option+drag on macOS and Shift+drag on Windows/Linux. While a selection is up, pointer movement is withheld from the program too: its own movement reports would otherwise wipe the selection before the user could reach Copy, and that walk is a long one here, because the pane context menu is reached from a button in the title bar rather than by right-clicking where the selection already is. Both reservations are scoped to this kind of pane — where nothing is reporting the mouse there is no selection at risk, and withholding events would only starve the terminal's own link-hover detection.
_Avoid_: mouse mode, mouse capture, tracking pane

**Mouse-blocked pane**: A **terminal pane** that refuses to hand the mouse to its foreground program — the default for every pane, seeded by the *Block mouse reporting* setting. The refusal is a swallowed DECSET: the request never reaches xterm, so the pane behaves as though the program had never asked, and ordinary click-drag selection and right-click both keep working. The pane remembers which modes it refused, because a program asks once and never again — so lifting the block hands them over there and then, rather than leaving the user with a setting that appears to do nothing until they restart the program. Lifting it is per pane, through the **mouse badge**; the setting supplies only the starting position.
_Avoid_: mouse-disabled pane, muted pane, mouse-off pane

**Mouse badge**: The glyph in a **terminal pane**'s title bar reporting that pane's relationship to the mouse — one state for a **mouse-reporting pane**, another for a **mouse-blocked pane** whose program has actually asked and been refused — which, clicked, flips the pane between them. A pane whose program never asked for the mouse carries no badge at all, so the badge's presence means "this program wants the mouse" and its state means "and here is who has it". Distinct from the **status icon** beside it, which reports the agent's state and is not a control.
_Avoid_: mouse button (that names a physical button), status icon, mouse toggle

**File pane**: A Pane that holds one open file — rendered as a Monaco editor (text), diff view, or image viewer depending on file type. Identified by its `filePath`. A diff-mode File pane and a text-mode File pane for the same underlying path are tracked independently (keyed `path` vs `diff:path`) and can be open simultaneously — e.g. the **Git changes tab**'s "Open File" action opens the latter without closing the former, and each stays in sync with on-disk changes via the file watcher independently of the other.
_Avoid_: editor, viewer

**Section** (Git changes tab): A group of rows defined by a **pair of git endpoints** being compared — `untracked`, `unstaged` (index vs worktree), `staged` (HEAD vs index), `against_base` (merge-base..HEAD, committed history only). The **Conflicted section** is the deliberate exception: a *state*, not an endpoint pair. See the flagged ambiguity below.
_Avoid_: group, category, bucket.

**Dirty workspace**: A git **Workspace** whose working tree holds uncommitted work — at least one untracked, unstaged, staged or conflicted path (what `git status` would list). A yes/no fact about the folder, answering "would I lose something if this folder vanished?". Commits ahead of the base branch do **not** make a Workspace dirty: the `against_base` **Section** is committed history, so a clean branch with unpushed or unmerged commits is still clean. A non-git Workspace is never dirty. Shown for every git Workspace in the **Left sidebar**, opened or not: an opened Workspace's dirtiness is live, while a not-yet-opened one's is re-checked only when the Window regains focus or the Workspace list changes, so it may lag until then. (Agents run in opened Workspaces, so an unopened one mostly changes from outside Abundio — which the user returns from by focusing the Window.) The same test escalates the **Remove worktree** confirmation. Drawn as the **Dirty marker**: a warning-coloured bar down the **right edge** of the Workspace's row, in both sidebar widths, present only while dirty. Full strength even on a not-yet-opened Workspace's row — uncommitted work nobody is looking at is the case it exists for. The right edge because the left one is the **Active workspace**'s accent; the row *background* is deliberately not used, since it already carries active and hover, and on a real Workspace list most rows are dirty at once — a colour across most of the list stops meaning "look here". The one place the bar cannot go is a **Folded set**'s hidden members, whose rows are not drawn at all: there the marker is a small **hollow ring** on the **Hidden rollup** instead. Hollow, because in the sidebar a *filled* circle is always a status badge (amber meaning Working), so the shape, not just the colour, keeps git state and PTY status apart.
Not to be confused with the **Branch stat**.
_Avoid_: dirty dot (the "dot" wording is retired for the **Status indicator** and would invite confusion with it), changed workspace, modified workspace ("changes" already names the **Git changes tab**'s Sections, which include committed history).

**Branch stat**: The `files +added −deleted` figure on a git Workspace's **Left sidebar** row — how big the branch is against its base, *including* uncommitted work (every **Section** of the **Git changes tab** summed). Its file count is **distinct paths**: a file listed in several Sections (committed on the branch *and* edited again) is one file. Shown only for opened Workspaces; its tooltip names the base it is measured against. Deliberately a different fact from the **Dirty marker**: a clean branch with commits ahead of its base shows a Branch stat and no Dirty marker, which is correct.
_Avoid_: change count, uncommitted changes (it counts committed history too).

**Conflicted section**: The first **Section** of the **Git changes tab**, listing the repository's unmerged paths. Sourced from the git index's conflict stages, not from a status walk; its rows carry no line counts, because an unmerged path has no stage 0 and so no honest numstat. Clicking a row opens an editable **file pane** — the only section whose rows do not open a diff pane.
_Avoid_: merge section, conflicts panel, unmerged panel.

**Row menu** (Git changes tab): The right-click menu on a single file row, deliberately **read-only** — Open Diff, Open File, Reveal in Finder, Copy Relative Path, Copy Path. It holds no git writes (no Stage, Unstage or Discard) and no terminal handoff, because **Resolve & stage** remains Abundio's one deliberate writer to the git index (ADR-0029), and an item that types `git restore` into a **Pane** would destroy work by a route that merely looks read-only. Opened only on a file row, never on a **Section** header or empty space. The same menu, in the same shape, is on a file row inside an expanded **Commits** row: there Open Diff opens that commit's **Commit diff pane** (disabled for a binary file), while Open File, Reveal and the copied paths are the file as it is on disk now — so a path the commit deleted has them disabled, like a deleted row. Right-clicking does *not* select the row — selection opens a **file pane**, and asking what a menu contains must not open a pane — so the row carries a separate transient highlight that clears with the menu. Items that cannot apply to a row (Open File and Reveal on a deleted path, Open Diff on a **Conflicted section** row) are shown **disabled, never hidden**, so the menu keeps one shape on every row. Reachable from the keyboard on a focused row (Shift+F10 or the ContextMenu key), where it is positioned against the row's box rather than a pointer. The row it was opened on is captured **by value**: a refresh that removes the row leaves the menu open and its path actions still correct.
_Avoid_: file actions menu, git context menu, right-click menu (all fine colloquially, but "Row menu" scopes it to the one thing it attaches to).

**Merge view**: A transient multi-pane arrangement for one conflicted file — read-only **Current side** and **Incoming side** panes above the editable file pane holding the file itself, with an optional **Base** pane. Toggled from the conflict toolbar; torn down automatically once the path is no longer unmerged. Not a distinct editor — ordinary **Panes** in the tab's split tree. See ADR-0030.
_Avoid_: merge editor, 3-way editor, conflict editor, merge pane.

**Merge side pane**: A read-only **Pane** showing one index stage of its **source pane**'s conflicted file. Owns no file — it mirrors a stage, the way a **Preview pane** mirrors a buffer, and shares that pane's derived shape (ADR-0001).
_Avoid_: stage pane, side editor, ours pane, theirs pane.

**Conflict block**: One `<<<<<<< / ======= / >>>>>>>` region within a file's text, comprising a **Current side** and an **Incoming side**, plus an ancestor side when the user's `merge.conflictStyle` is diff3/zdiff3. Abundio recognises a marker by git's own rule — exactly seven characters at column 0 followed by a space or end-of-line — so the two never disagree about what is conflicted.
_Avoid_: hunk (a diff term), conflict hunk, merge chunk, conflict region.

**Current side / Incoming side**: The two halves of a **Conflict block**, named after the labels git writes into the markers. Deliberately *not* "ours"/"theirs", which invert during a rebase (git replays your commits onto upstream, so stage 2 is the upstream side). Those names stay in Rust, where they are git's index vocabulary; the IPC layer is the boundary.
_Avoid_: ours, theirs, local/remote, left/right, mine/yours.

**Resolve & stage**: The only write Abundio performs on a conflict — save the buffer, then `git add` the path. It does not finish the operation; `git merge --continue` (or the rebase/cherry-pick equivalent) stays with the user in a terminal **Pane**. See ADR-0029.
_Avoid_: merge, finish merge, complete merge, commit the merge.

**Preview pane**: A Pane that renders a live, read-only rendering of its **source pane**'s markdown buffer — including Mermaid diagrams. Owns no file of its own; it mirrors. Created beside a file pane when a markdown file is opened. Its appearance is governed by the **Preview color mode**.
_Avoid_: render pane, markdown viewer

**Preview color mode**: A global, persisted user preference governing every **Preview pane**'s appearance. Binary: **follow theme** (the default — the preview adopts the active theme's *actual colours*: its canvas, text, borders, links and accents match the rest of the UI) or **printed paper** (forced pure-white "document" look regardless of theme). There is no forced-*dark* state — a dark preview arises only because the active theme is dark. Toggled from the preview's title bar — Settings ▸ Editor points at that toggle rather than duplicating it. Follow-theme remaps the document **surface** only; code-block **syntax-highlighting** token colours stay at the rendering library's light/dark defaults (themes carry no syntax palette). **Print** always renders on white paper, ignoring this preference. See ADR-0013.
_Avoid_: preview theme, dark mode

**Dim slot**: The ANSI colour-8 palette position (xterm's `brightBlack`), whose role is to *recede* — it is what a program reaches for when it wants text that is present but subordinate to what the user typed. zsh-autosuggestions' default `fg=8` is the case that matters most, since the suggestion sits inline with the command being typed. Its contract: the Dim slot must lie **between the background and the foreground in luminance, nearer the background**, and at least **2:1** away from the foreground. The ratio alone is not the test — direction is part of it, or a slot that is *heavier* than the body text passes the number while reading as emphasis (Solarized Light ships colour 8 as near-black `#002B36`, a comfortable 3.37:1 from its foreground and entirely the wrong way round). Crucially the contract binds the **effective** colour, after xterm's contrast correction has been applied — never the value declared in `themes.ts`. That correction steps in 10% increments and stops past its target, so it is modelled by porting it rather than approximating it. Solarized Dark declares colour 8 as `#002B36`, byte-identical to its background; the correction lifts it to a readable grey that lands within 1.05:1 of the foreground, so a theme whose declared value looks fine can still have no usable Dim slot. Only slot 8 carries this contract: slots 7 and 15 are *supposed* to equal the foreground, and the chromatic slots owe their hue, not their dimness.
_Avoid_: dim colour (collides with the DOM-layer dimming in `abundio-side-dim`), faint colour (ECMA-48 "faint" is SGR 2, a different mechanism — xterm renders it as 50% alpha of the foreground and we do not touch it), suggestion colour (names one consumer, not the role), bright black (the ANSI slot name, and a lie on most themes).

**Source pane**: The file pane a preview pane is bound to (`sourcePaneId`). The preview reflects this pane's unsaved buffer and follows it when a new markdown file is opened in it.

**Tab**: A named pane layout within a Workspace. Each tab has its own root `PaneNode`.
_Avoid_: view, screen

**Note**: A single per-Workspace rich-text scratchpad (free text + checklists), edited in the right sidebar's Notes tab and stored as TipTap JSON. Exactly one per Workspace; autosaved. See ADR-0012.
_Avoid_: memo, scratchpad, comment

**PTY**: A pseudo-terminal process bound to a Pane. Identified by a `ptyId` string. Spawned on first render; IDs from previous sessions are cleared on load.
_Avoid_: terminal process, shell

**Agent**: An AI coding CLI tool (Claude Code, Copilot, Gemini CLI, Aider, Codex, OpenCode, Qwen Code, Kimi Code, Grok Build, or a user-added one) that can be launched inside a Pane. Not spawned until the user requests one. Two independent facts are kept about each: whether it is **Installed** on this machine, and whether it is **Watched** by Abundio. They are deliberately separable — an Installed Agent the user switched off stays off, and a Watched Agent that is not Installed is merely an offer that will fail.
_Avoid_: "detected agent" unqualified — say **Installed** or **Watched**; the bare word "detection" has meant both, and also the runtime title/process match that decides a Pane is in **agent mode**.

**Installed**: True of an **Agent** whose command resolves to a file on the user's login-shell `$PATH` (plus `/usr/local/bin` and `/opt/homebrew/bin` on macOS). A live fact about the machine, re-read on every scan and never stored: Abundio owns no opinion here, it only looks. Shown per Agent as the green *Detected* badge in Settings ▸ Agents, and it is the one thing that badge means. The scan resolves the real login+interactive `$PATH` by running the shell once, so it can time out and under-report — which is why a scan that finds *nothing* is treated as a failed scan, not as a machine with no Agents.
_Avoid_: available, present, on PATH (fine in prose, but the noun is Installed)

**Watched**: True of an **Agent** Abundio should act on — offer in the launch menus, match against terminal titles and process names to put a Pane into **agent mode**, and provision **Agent hooks** for (subject to the **Status Hooks setting**). The per-Agent toggle in Settings ▸ Agents, persisted as `enabled`, and the user's to set. Its *starting* value comes from **Agent seeding** on a first run; after that nothing but the user changes it.
_Avoid_: enabled (the persisted field's name, but it says nothing about what is enabled), active, detected

**Agent seeding**: The one-time act, on a genuinely new install, of setting each built-in Agent's **Watched** flag from whether it is **Installed** — so a new user's launch menus and hook provisioning start out describing their machine rather than listing all nine built-ins. Runs once per install, claimed atomically through the app-global `settings` table so a second **Window** cannot re-run it; skipped entirely for an existing install, and skipped when the scan finds nothing at all (read as a failed scan). Afterwards it is only ever re-run by the user, from the *Match toggles to installed agents* action in Settings ▸ Agents.
_Avoid_: auto-detection, auto-enable (both suggest a standing rule; seeding happens once and then the user owns the switch)

**Prompt action**: A stored, named, parameterised prompt a user can fire at a running **Agent** with one click. Carries a body (with placeholders), a **parameter** list, and a **scope**. Firing it writes the resolved body into the **Pane**'s PTY as bracketed paste followed by a bare `\r` — it **submits**. Alt/Option-clicking the button omits the `\r`, staging the text in the Agent's prompt box so the user can add to it before sending. There is no per-action "auto-submit" flag: the click is the confirmation, and for a parameterised action the dialog's Send button is a second one. Nothing is sent that the user did not author, which is why this may submit where **File drop** may not.
_Avoid_: preset (claimed by the dead `agent_presets_json` column on the `workspaces` row — carried since `001_init.sql`, read by nothing but fixtures, verified empty across every row, and still present pending a separate cleanup), prompt template (names the body, says nothing about the send), quick prompt, macro, snippet.

**Draft**: A **Prompt action** with no body yet. Settings creates the row and the user fills it in afterwards, so a body-less action is a normal intermediate state, not an error — storage accepts it. It is **never offered**: `actionsForPane` skips it, so it reaches no **Action bar** and no **Palette firing**, because a button that pastes nothing and then submits would send an empty prompt to a live Agent. Settings shows it with a *Needs a body* flag rather than hiding it. The same shape as an action whose **Action scope** set has emptied out — kept, shown where it is edited, never offered where it would fire. The in-pane popover cannot create one: it is a create-and-go flow and keeps its Add disabled until the body is filled.

**Action scope**: Which **Agents** a **Prompt action** is offered for. Either `all` — every Agent, including ones added after the action was authored — or an explicit **set** of Agent ids. The two are distinct values, not one expressed as the other: a set naming all nine built-ins must *not* pick up a tenth Agent the user adds later, and `all` must. Scope names Agent *types* (Claude Code, Copilot), never a running **agent-mode PTY**; slash commands are agent-specific, which is why an action authored from a Pane defaults to that Pane's Agent rather than to `all`. An action whose set empties out (its only Agent was deleted) is kept, shown in Settings as selecting nothing, and never rendered in an **Action bar** — deleting it is the user's call.
_Avoid_: per-agent (ambiguous between the type and the instance), agent filter, applies-to.

**Firing**: Activating a **Prompt action**. Parameters are collected first (any action with one or more **Parameters** opens the parameter dialog; an action with none fires straight from the click), then the body is resolved and written to the **agent-mode PTY** as one bracketed paste — via the same `term.paste()` path **File drop** uses — followed by a bare `\r`. Interpolated Parameter values are stripped of C0/C1 controls, reusing `fileDrop`'s `stripControlChars`: a value pasted from a web page or from an Agent's own output can carry `ESC[201~`, which closes bracketed paste early and runs whatever follows. The **body is deliberately not stripped** — it is author-written and its newlines are the point. Refused while the Agent is **Waiting**: a permission prompt has redefined what keystrokes mean, so the paste would answer a question the user never read, and writing to the PTY would additionally tell the status machine the user had responded. **Working** does not block firing — queuing a follow-up mid-turn is a real workflow.
_Avoid_: triggering, running, executing (collides with shell execution), invoking.

**Prompt action store**: Where **Prompt actions** live — a dedicated SQLite table, one row per action, reached over IPC, **not** `settingsStore`/`localStorage` where every other global setting sits, and **not** a JSON blob in the key-value `settings` table. The reason is the **in-pane popover**: authoring is frequent, mid-session, and possible from any **Window**, while the Settings window may be open editing the same list. `localStorage` is isolated per Tauri webview, so cross-window sync ships the changed value in a broadcast payload and the receiver overwrites its own copy — fine for a font size, lossy for a list two windows append to, where one whole array silently wins. User-authored content is a different class from a preference. A JSON blob keyed into the `settings` table would not fix it either: SQLite serialises the write but not the read before it, so two Windows appending still lose one. Row-per-action does fix it, because two inserts do not conflict. The broadcast still fires, but carries only *"the list changed, re-read it"*, so there is no array to clobber. See ADR-0039.
_Avoid_: preset store, settings (it is not in settingsStore).

**Action bar**: The horizontally-scrolling strip along the bottom of a terminal **Pane**, rendering the **Prompt actions** available to that Pane. Present in **every** Pane whose PTY is in **agent mode** (`activities[ptyId].detectionMode === "agent"` — the canonical signal the status indicators and **File drop** read, not `agentPtyIds`, which is kept in lockstep with it but is not the source of truth), **including when it holds nothing**. An empty bar shows an *Add a prompt action* invitation instead of buttons, and drops the trailing `+` so there is only one way in. Presence does not depend on how many actions exist: nothing is seeded on a fresh install (a stock `/review` button would assume a slash command only some installs have, and fail on first click), so a bar that hid itself when empty would leave the feature with no visible entry point at all. It costs one terminal row, and it removes the appear/disappear refit that a count-dependent bar would cause on every authoring change. Appearing and disappearing with **agent mode** still refits xterm, on every Agent launch and exit; the space is not reserved.

A Pane can be in agent mode with no resolved **Agent** id — the auto-launch path knows only the command string, and the id is backfilled later by a title match or the first Agent hook — so the bar shows the global-scoped actions immediately and the agent-scoped ones flow in when the id resolves. Degrading to global-only is deliberate: a custom Agent whose id never resolves still gets a usable bar. This differs from the title bar, which withholds Agent *identity* until the id is known: identity is better silent than wrong, capability is better partial than absent.

Contents are ordered agent-scoped first, then global, each in the user's authored order (reorderable in Settings); there are no group headers, the strip is too short for chrome. A button carries its **position number** as a **powerline segment** — a filled block with the digit knocked out, closed by `U+E0B0`, the solid right-pointing separator every powerline and starship prompt is built from, drawn in the segment's own colour against the bar's transparent background so the block appears to taper into the terminal. The glyph needs no fallback: Abundio *bundles* its terminal fonts and every one is a `… Nerd Font Mono` variant, with `--font-mono` defaulting to one. The separator is sized to the bar's full height rather than the 11px label, because powerline glyphs are drawn to fill their whole cell — at the text size it renders as a small arrowhead floating mid-line instead of a tapering edge — and the block is padded wider than the digit needs, or the two read as equal halves of an arrow rather than as a segment with an edge. A **Waiting** bar keeps the shape and loses the colour, so it reads as "not now" rather than as a different design. **Sending pulses the segment**: one brightening beat, plus a highlight that sweeps the button left-to-right, because the prompt travels *out* of the pane. It is emitted from **Firing**, not from the click — a parameterised action opens its dialog first, so pulsing on click would fire for a send that has not happened and again if the user cancels. Both halves stand down under `prefers-reduced-motion`. A button also carries its name, plus a trailing `…` when the action has **Parameters** — the macOS menu convention, and it matters here because a click submits, so the ellipsis is the warning that you will be asked something first. Long names truncate to a tooltip carrying the full name and a preview of the resolved body; that preview is the only place the user can see what a button will actually say to their Agent before sending it. No icons and no per-action colour: an icon picker is a sub-UI of its own, and a row of coloured chips fights whatever theme is active. Overflow scrolls horizontally with vertical wheel mapped to horizontal and fade masks at the live edges — no scrollbar, no arrows. A Prompt action appears here only if its **Show in bar** flag is set; the **Command palette** offers every in-scope action regardless, so the bar is the set you reach for rather than the complete index.
_Avoid_: toolbar, quick bar, prompt bar, button strip.

**Editing from the bar**: Right-clicking a bar button opens a menu for *that* **Prompt action** — Edit, hide/show in the bar, delete — rather than the pane's own context menu. **Delete asks first**, from both here and Settings: there is no undo and no down-migration, and this menu is a small right-click target where a misclick is easy. The confirmation names the action and says where it will disappear from. It is routed through the pane's existing `contextmenu` listener via a `data-prompt-action-id` attribute on the button, **not** a handler on the button itself: that listener is registered in the **capture** phase and calls `stopPropagation` unconditionally (it must, because xterm's own listener moves a hidden textarea under the cursor, which on Windows WebView2 pastes the clipboard straight into the PTY), so a bubble-phase handler on the button could never run. Bar buttons are `select-none`; a right-click that highlighted the label would be an odd thing to leave behind. Edit reuses the authoring popover rather than a second component — the fields are identical and two would drift — and an edit keeps a scope set authored in Settings intact rather than collapsing it to the current pane's Agent.

**Parameter**: One value a **Prompt action** asks the user for before it fires, substituted into the action's body where its placeholder sits. Five types, chosen for *which widget to show and what text the value becomes* — everything bottoms out in text, because the destination is a prompt: **text** (a one-line input that grows into a textarea on Shift+Enter; Enter submits the dialog), **number** (validated before send, interpolates identically to text), **choice** (a fixed list the author defines), **toggle**, and **attachment**. There is deliberately no *object* type: a field you type JSON into is already a text field, so the only thing object could add is path traversal (`{{config.retries}}`), and that needs defaults, then iteration, then a template engine living inside a terminal multiplexer.
Parameters are **derived from the body, never declared beside it**: typing `{{path}}` creates the Parameter, and its name exists in exactly one place. That makes a placeholder with no Parameter, and a Parameter no placeholder uses, structurally impossible rather than merely warned about. Dialog field order is order of first appearance in the body, which is also the order the sentence reads in. A placeholder used twice is one Parameter. Renaming a placeholder drops that Parameter's type and default, since the name is the key — accepted, because the alternative is guessing which edit was a rename.
The two authoring surfaces share **one** parameter editor (`components/PromptActions/ParameterEditor.tsx`), rather than each carrying its own. The popover is deliberately the smaller editor overall — reordering, duplication and deletion stay in Settings — but everything needed to *finish defining a parameter* has to exist in both, or the popover can mint a **choice** with no options (an empty dropdown) or a **toggle** that contributes nothing. _Avoid_: field, argument, variable, input (all fine in prose; the noun is Parameter), long text (merged into text).

**Required**: A per-**Parameter** flag, on by default, and **absent means required** — so a Parameter authored before the flag existed keeps the behaviour it was written against. The parameter dialog's Send stays disabled until every *required* Parameter is filled. A **toggle** is never required: both of its states are meaningful and the author wrote text for each, so there is nothing to supply.

An **optional** Parameter left empty does not resolve to `""` — that leaves a hole in the sentence (*"Review the file:  focusing on ."*). Its placeholder is erased **together with the whitespace around it**, and a line containing nothing but that placeholder is dropped entirely. This is the smallest cleanup that reads correctly: it closes the gap the removal opened and nothing else. It is **not** a conditional-section engine — the author still cannot mark arbitrary prose as belonging to a Parameter, and `{{#if}}` stays out of scope.

A Parameter may carry an **authored default**, pre-filled when the dialog opens; the dialog deliberately does **not** recall the last value used, because Enter submits the dialog and firing submits to the Agent, so a reflex Enter would send a three-day-old value nobody read.

**Toggle parameter**: A boolean **Parameter** that contributes *author-written text*, not a literal. The author supplies the string to insert when on (and optionally when off), and the placeholder resolves to one or the other. Interpolating `true`/`false` into a prompt was the obvious reading and is near-useless — no Agent does anything sensible with "thorough: false" — and conditional body sections (`{{#if …}}`) are the template engine this design refuses to build.

**Attachment**: A **Parameter** whose value is one or more files, supplied by file picker or the **Paste from clipboard** button in the parameter dialog (a button, not Cmd+V: WebKit fires `paste` only on an editable element) — **not** drag-drop: OS file drops arrive app-wide from Tauri and are already owned by **File drop**, which targets panes, so intercepting them for a modal would fight it. It resolves to the file **path(s)**, interpolated into the prompt like any other Parameter — Abundio never writes the OS clipboard and never synthesises a `Ctrl+V`, which is the reverse of **Smart image drop**. Paste from clipboard reads the OS clipboard in Rust (never writes it). Files copied in Finder/Explorer attach by their own paths — checked **before** the image, because Finder also puts a copied file's *icon* on the clipboard as a picture. Copied folders are dropped (a clipboard holding only folders is an error, not a fall-through to that icon), and more than 32 files is refused. Otherwise the image has no path, so it is saved as a content-hashed PNG under the versioned root's `prompt-attachments/` — always PNG, because the clipboard hands over decoded pixels, not the source file, and scaled so its longest side is at most 4096 px, which keeps most photos under the 25 MB limit (one that is still over is re-encoded once at 2048 px) — a directory treated as a cache and swept by age at startup, not as user data. See ADR-0038.
_Avoid_: upload, image paste (belongs to Smart image drop), file drop (belongs to the terminal-pane drop).

**Show in bar**: A per-**Prompt action** flag, on by default, deciding whether the action renders in an **Action bar**. Off does not narrow the action's **scope** — it stays fully available from the **Command palette**. It exists so a user with forty actions keeps a usable bar; without it the bar degrades into an unscrollable index as the list grows.
_Avoid_: hidden, disabled, pinned (inverts the default).

**Position number**: The 1-9 badge on an **Action bar** button, and the digit that fires it — `Cmd+1`…`Cmd+9` on macOS, `Ctrl+Shift+1`…`Ctrl+Shift+9` on Windows/Linux. It is **positional**, a property of where the button sits in the bar being looked at, *not* a property of the **Prompt action**. The two diverge, because agent-scoped actions sort ahead of global ones: the same action is number 2 in a Pane with no agent-scoped actions and number 7 in a Pane with five. Positional wins because the number's whole job is answering "which key fires this button", and an authored number that disagrees with the visible order fires the wrong prompt at a live Agent — unrecoverable, since **Firing** submits. Stable muscle memory comes from reordering in Settings, per Agent, not from pinning numbers to actions. Only the first nine buttons are numbered; the rest are reachable by click or **Palette firing**.
_Avoid_: index, hotkey number, slot.

The bindings are chosen to be invisible to the terminal, not merely unused by Abundio (which binds no digits at all). macOS `Cmd` is not a terminal modifier, so xterm.js never forwards a Cmd-chord to the PTY and no Agent can see it. On Windows/Linux `Ctrl+<digit>` is unusable — `Ctrl+2` is NUL, `Ctrl+3` is ESC, and so on across the row — and `Ctrl+Alt+<digit>` is unusable too despite matching the split-pane precedent, because `Ctrl+Alt` **is AltGr** on European layouts and would swallow characters the user needs to type.

**Palette firing**: The **Command palette** is the second way to fire a **Prompt action**, and it targets the **focused pane**. It lists Prompt actions only while that pane is an **agent-mode PTY**, filtered by **Action scope** — the same set the **Action bar** would show, minus the **Show in bar** filter — and disabled while the Agent is **Waiting**, matching the bar. Never a "which pane?" follow-up question: the user answered that by focusing a pane before opening the palette. The alternative, listing everything and choosing a target on fire, would let a prompt be typed into a **shell-mode PTY** and submitted, which is arbitrary shell execution of prompt text, not a wrong-pane annoyance. Clicking a button in an unfocused Pane focuses it first (as **File drop** does), and focus lands in the terminal afterwards, never on the button.

**Turn**: One unit of Agent work — from a prompt submitted (turn-start hook) to the turn finishing or failing (turn-finished / turn-failed hook), or, when neither hook ever arrives, to a **Presumed end** inferred from silence (ADR-0027). If the Agent spawned background **Subagents** that outlive the turn-finished hook, the Turn extends until the last of them stops — delegated work is the Turn's work, so its duration and **Working** time include the subagent tail. A new prompt always cuts the extension short: turns never overlap, so a Subagent surviving into the next Turn accrues its remaining time there (accepted imprecision). The extension applies only to a Turn that *finished* — a **Turn failure** has no tail: its Subagents are dropped when the user acknowledges the **Error**, so an orphaned set can't hold the next Turn's turn-finished hook (ADR-0022, ADR-0026). A **Mid-turn failure** does not end the Turn at all. The atomic record for agent telemetry: one row per Turn in the `agent_turn` table, carrying its duration, **Working**/**Waiting** time, permission/tool/error counts, and the lines it changed. See ADR-0018.
_Avoid_: run, request, interaction (and never "running" — collides with **Working**).

**Subagent**: A worker an **Agent** spawns to delegate part of a **Turn** (Claude/Codex/Qwen/Kimi subagent hooks, Grok `SubagentStart`/`SubagentStop` with a `subagentId`, Copilot `subagentStart`/`subagentStop`, OpenCode child sessions with a `parentID`). Abundio observes only its start/stop lifecycle, and only to hold the parent PTY in **Working** until all Subagents finish — a Subagent has no Pane, no status icon, and no telemetry row of its own.
_Avoid_: background agent (not all are background), task (collides with OpenCode's task tool), child session (OpenCode-specific).

**Session**: The span of one Agent process in a Pane — from launch to `SessionEnd`/exit — comprising one or more **Turns**. Not a stored entity: it's a `session_id` stamped on each Turn so the **Statistics overlay** can group a session's Turns and answer "how long was the agent running". See ADR-0018.
_Avoid_: conversation, run.

**Statistics overlay**: A per-**Window**, full-area surface that covers the **workspace stack** (terminals stay alive behind it via the portal registry) to show agent **Turn** telemetry — working-vs-wall-clock time, lines changed, per-agent and per-workspace breakdowns, an activity heatmap, and recent Turns — for the Window's **Active profile** over a selectable range (week/month/year/all). Launched from the one interactive control on the **Overview bar**; closed with its own button or Esc. Profile-scoped, so it refetches when the Active profile changes. See ADR-0018.
_Avoid_: dashboard, stats panel (collides with retired "panel"), stats view/screen (collides with **Tab**).

**Agent hook**: A lifecycle event an Agent emits — prompt submitted, permission requested, turn finished, turn failed — that Abundio observes (via the Agent's own hook system) to drive the status indicator. Abundio only observes; it never alters the Agent's behaviour. Distinct from **Hook provisioning** (the edits Abundio writes so these events reach it).
_Avoid_: callback, event listener

**Hook provisioning**: The set of edits Abundio writes into an Agent's *own* configuration so that Agent emits its **Agent hooks** to Abundio — distinct from the hooks themselves, which Abundio only observes. Comprises the relay scripts in Abundio's data dir plus, per Agent, either entries merged into a co-owned config (e.g. `~/.claude/settings.json`, `~/.gemini/settings.json`, `~/.qwen/settings.json`, `~/.kimi-code/config.toml`) or an Abundio-owned file (e.g. `~/.codex/hooks.json`, `~/.copilot/hooks/abundio.json`, `~/.config/opencode/plugin/abundio.ts`, `~/.grok/hooks/abundio.json` — Grok's personal-scope hooks dir is always trusted, unlike its project-scope hooks which sit behind a folder-trust gate). Gated by the global **Status Hooks** setting; idempotent; removes only Abundio's own entries on disable. See ADR-0003.
_Avoid_: hook injection, hook registration (ok colloquially)

**Status Hooks setting**: The global, opt-out toggle (`agentHooksEnabled`) that turns **Hook provisioning** on or off. On by default. Provisioning of a given Agent is gated by **both** this global toggle and that Agent's own per-Agent toggle (the **Watched** toggle): an Agent gets hooks only when both are on, and toggling an Agent off removes just its hooks (toggling it back on reinstalls them, if the global toggle is on). The **Provisioning footprint** display in Settings ▸ Agents is read-only — the Agent's existing enable toggle is the per-Agent control.
_Avoid_: hooks preference

**Provisioning footprint**: The concrete, per-Agent record of what **Hook provisioning** has done — which config file is touched, whether Abundio owns that file or merged into a shared one, and which lifecycle events are hooked — surfaced read-only per Agent in Settings ▸ Agents. Each Agent reads as one of: *Registered*, *Not registered*, *Not installed*, *Not supported* (Aider and custom Agents have no hook integration), or *Config error* (the Agent's config is unparseable).
_Avoid_: hook status (ambiguous with the **Status indicator**)

**Waiting**: An Agent state in which the Agent has emitted a permission- or input-request hook and the user has not yet responded in its terminal. Distinct from a finished turn ("ready") — the Agent is stalled mid-turn, not done.
_Avoid_: blocked, idle, stuck

**Working**: A PTY state in which work is in progress — an **Agent** mid-turn (between turn-start and turn-end hooks, not blocked on a permission/input request) or a **shell-mode PTY** between the shell-integration `command_start` and `command_end` markers. Distinct from **Waiting** (agent-only — blocked on the user) and from a finished turn/command. The status indicator differs by mode: agent-Working is the amber broken double-ring spinner (a warm "attention, watch progress" colour), shell-Working is the cyan breathing triple-chevron `>>>` (a cool "neutral throughput" colour — you started the command, no alarm needed).
_Avoid_: active (collides with **Active workspace**), busy, running

**Ready**: An **Agent** state in which the Agent finished its turn cleanly and the user has not yet acknowledged it (by focusing or typing in its pane). Shown as the purple status indicator. Distinct from **Idle** — Ready is a notification, Idle is the rested state after acknowledgement. **Shell-mode PTYs do not have a Ready state**: a clean command exit transitions straight to **Idle** — for a shell, the output that just rendered is itself the "you have something to look at" signal, and a separate notification state would be redundant. Only the **Error** state is surfaced for shells.
_Avoid_: finished, done, complete

**Idle**: A PTY's resting state — no work in progress, and the last finished turn or command (if any) has been acknowledged by the user. Also the default state for a freshly initialised PTY. Shown as the green status indicator.
_Avoid_: inactive, asleep

**Error**: A PTY state in which work failed — an **Agent** emitted a failure hook (or its turn exited non-zero in agent mode), or a **shell-mode PTY**'s last command exited with a non-zero code that isn't a user-stop (130/143). Shown as the red status indicator. Comes in two kinds, distinguished by the **Status event** that caused it and not by the icon (both are red): a **Turn failure** ended the **Turn** — acknowledging it goes to **Idle** and drops any live **Subagents**; a **Mid-turn failure** is an operation inside a Turn that failed while the Agent kept generating — acknowledging it returns the pane to what it was doing (**Working**, or **Waiting** if it was blocked on the user), and the Turn still ends **Ready** if it completes. Only a Turn failure raises a notification. See ADR-0026.
_Avoid_: failed, broken, crashed

**Turn failure**: An **Error** that ended the **Turn** — Claude/Kimi/Qwen `StopFailure`, Grok `Stop{reason:"error"}`, a non-zero PTY exit, or a shell command's non-zero exit. Nothing more is coming, so acknowledging it rests the pane at **Idle**.
_Avoid_: fatal error, hard error

**Presumed end**: A **Turn** boundary Abundio *inferred* from silence rather than observed from an **Agent hook** — the pane went quiet past the idle backstop window and the Agent never said the Turn ended. Recorded under its own end reason so a guessed boundary is never read as an observed one, and timed from the last activity rather than the moment we gave up, so the silence isn't billed as work. Distinct from the **Subagent**-drain backstop, where the turn-finished hook *was* observed and merely held for the tail — there only the timing is fuzzy, not the fact (ADR-0022). See ADR-0027.
_Avoid_: timeout (implies we imposed a limit on the Agent), stale (collides with the Subagent stale prune), abandoned (suggests the user walked away).

**Mid-turn failure**: An **Error** raised by an operation *inside* a **Turn** that the **Agent** carried on past — currently only Copilot's `errorOccurred`, which is always followed by a turn-finished hook. The pane goes red immediately, but the Turn is still open, so acknowledging the red must not claim the Agent went **Idle**. Counted against the Turn's error count without ending it.
_Avoid_: recoverable error (we only know the Agent kept going, not that it recovered), transient error, warning

**Status indicator**: The coloured **status icon** Abundio shows for a Pane — and aggregated up to its Tab and Workspace — reflecting its PTY's current state. The state set differs by **PTY mode**: an **agent-mode PTY** can be Idle / Working / Waiting / Ready / Error; a **shell-mode PTY** can only be Idle / Working / Error (no Ready, no Waiting). Aggregation is split by mode: a Tab and a Workspace each carry an **Agent rollup** (agent-mode PTYs only) and a **Terminal rollup** (shell-mode PTYs only), never one mixed icon — drawn together as a **Status composite**. Working is shown in **different colours by mode** — amber spinner for an Agent (warm, attention-worthy), cyan breathing chevron `>>>` for a shell (cool, neutral throughput).
_Avoid_: status dot — it renders as an icon (spinner, chevron `>>>`, check, coloured glyph), not merely a dot.

**Agent rollup**: The status icon a Tab or Workspace shows for its **agent-mode PTYs** only — the highest-precedence state among them (Error > Waiting > Ready > Working > Idle). A shell-mode PTY never contributes, not even its Error; that belongs to the **Terminal rollup**. With no agent-mode PTYs the rollup is **absent** (no icon), not Idle — an icon's presence means at least one Agent exists. The one exception is a Workspace never opened in this Window, which shows a single grey "Not opened" icon in its place. Drawn as the **Primary icon** of the **Status composite** whenever any Agent exists.
_Avoid_: tab dot, workspace dot, aggregate status

**Busy PTY**: A **PTY** with work in flight — an **agent-mode PTY** that is **Working**, or a **shell-mode PTY** with a command running. A pure function of one PTY's status entry, so the **Status indicator** and the close confirmations can never disagree about whether a terminal is busy. A shell that has fallen silent mid-command still counts: the **Status machine** suppresses its idle backstop while a command runs, so a long quiet build is Busy for as long as it takes. The single test behind the **Unload workspace** and **Close window** confirmations: no Busy PTY, no prompt. A **Waiting** agent is deliberately *not* Busy — it is blocked on the user, not mid-turn — with one exception: **Quit** asks for Busy *or* a Waiting agent, because quitting takes down every Window, including ones the user cannot see, and a Waiting agent holds a finished piece of work with a question on it. Idle shells, open editors and merely-opened Workspaces are never Busy, so a quiet Abundio now quits without asking: layouts, Workspaces and scrollback all come back on relaunch, and genuinely unsaved editor files keep their own separate confirmation.
_Avoid_: running agent (ambiguous — a Waiting agent is also "running"), active workspace (collides with **Active workspace**), busy workspace

**Terminal rollup**: The status icon a Tab or Workspace shows for its **shell-mode PTYs** only — Error > Working > Idle (shells have no Ready or Waiting). Working shows as the cyan `>>>`, as at the pane. Separate from the **Agent rollup** so each icon means one thing. Absent (no icon) when there are no shell-mode PTYs. Drawn as part of the **Status composite**: usually the small **Status badge**, or the **Primary icon** when the Workspace has no Agents at all.
_Avoid_: shell rollup, shell dot, terminal status (ambiguous — every Agent also runs in a terminal pane)

**Status composite**: The single mark a Tab or Workspace shows for its whole status — a **Primary icon** with an optional **Status badge** on its lower-right corner. Replaces the two equal, stacked icons of ADR-0032, which put two marks of identical weight on every row and left the reader to work out which one mattered. One composite per Tab, per sidebar row (both widths) and per **Hidden rollup**. Hovering it gives one tooltip covering both rollups, one line each, absent rollups omitted:
"Agents: 2 Waiting · 1 Working · 3 Idle" / "Terminals: 1 Working · 2 Idle". The tooltip is the one place a Terminal rollup's Idle count is always visible, so "my terminals are fine" and "I have no terminals" stay tellable apart even when the badge draws nothing.
_Avoid_: status pair, icon stack, combined dot

**Primary icon**: The larger, leading icon of a **Status composite** — the **Agent rollup** whenever the Workspace or Tab has at least one agent-mode PTY, otherwise the **Terminal rollup**. It is never displaced: a shell Error shows as a red **Status badge** beside a calm Agent icon rather than taking the primary slot, so the big icon always answers the same question ("what are my Agents doing?") and never changes what it is describing under the reader. Absent — nothing drawn at all — only when there are no PTYs of either kind. A Workspace never opened in this Window keeps its single grey "Not opened" icon here.
_Avoid_: main dot, big icon, agent icon (it is the Terminal rollup when there are no Agents)

**Status badge**: The small icon on a **Status composite**'s lower-right corner, always the **Terminal rollup**, and drawn **only** when the **Primary icon** is the Agent rollup and the Terminal rollup is Error or Working. A terminal's Idle never earns a badge — the badge exists to surface what wants attention, and idle shells are the normal case. When the Terminal rollup *is* the Primary icon it shows Idle as usual: the suppression is a property of the badge, not of the rollup. Offset outward so most of it falls outside the Primary icon's box, because every status glyph is a stroked outline and two overlapping outlines read as neither.
_Avoid_: corner dot, secondary status, overlay

**Status event**: The normalized *input* to the **Status machine** — a single fact about a **PTY** that may drive its status, regardless of source. Producers are an **Agent hook**, a shell-integration OSC marker (or its process-monitor fallback for `ShellType::Other`), a user keystroke, a PTY exit, or the periodic idle **Tick**. Consumed by the **status reducer** (and, at finer grain, by **Turn** telemetry); never observed directly by the UI. See docs/plans/status-machine.md.
_Avoid_: hook (that's one *producer*, not the event), signal (collides with OS signals), activity event.

**Status transition**: The enriched *output* of the **Status machine** — a record `{ ptyId, prev, next, cause }` emitted whenever a PTY's status tuple (icon state + **detection mode** + **Session**) changes, where `cause` is the **Status event** that drove it (or the idle backstop). The single seam every status consumer reads: the **Status indicator**/UI projects `next` → icon colour, notifications project `next ∈ {Ready, Error, Waiting}` + visibility, and **Turn** telemetry projects `cause` + `next`. Carrying `cause` in-band is what removes the former subscriber-ordering races. See ADR-0018, docs/plans/status-machine.md.
_Avoid_: status change event (verbose), state diff.

**Status machine**: The deep module that derives a **PTY**'s status — a pure **status reducer** (`(state, Status event) → state`, fully table-tested, with time supplied via the `Tick` event) plus a **dispatcher** that is the single home for *all* per-PTY status state (the icon state, **detection mode**, **Session**, and the hot activity-heuristic fields previously split across Zustand and out-of-band module Maps), runs the reducer, projects the icon-relevant slice into the store, and emits **Status transitions**. Distinct from the **Status indicator**, which is the *view* of the status the machine computes. Internal state names use the canonical **Working / Waiting / Ready / Idle / Error** (resolving the deferred `active`→`working` code rename). See ADR-0009, ADR-0015, ADR-0020, docs/plans/status-machine.md.
_Avoid_: activity store (the retired `ptyActivityStore` framing), status engine, state manager.

**Overview bar**: A horizontal strip across the top of the app window, between the **Titlebar** and the per-workspace tab row, showing glanceable global counts: **Opened workspaces** (out of total), each of the five **Agent** states (Idle, Working, Waiting, Ready, Error), the three **shell-mode PTY** states (Idle, Working, Error — shells have no Ready or Waiting, see ADR-0009), all aggregated across all opened workspaces, and the user's pending GitHub PR counts (review-requested and own open PRs, both **Profile-scoped** — see **PR scope** and ADR-0028 — and dimmed until the Profile's repository set resolves). The agent and shell counts are derived **live** from `ptyActivityStore` (no cached totals), so every path that closes a Pane/Tab/Workspace must purge that PTY's entries or the counts drift — see ADR-0020. Always visible. Its counts are **read-only** in the sense that it never *mutates* app or workspace state; it carries exactly one **navigation affordance** — a right-aligned button that opens the **Statistics overlay**. The only piece of global chrome that lives between the Titlebar and the workspace stack. See ADR-0005, ADR-0018, ADR-0019, ADR-0028.
_Avoid_: metrics bar, status bar (already taken — bottom of window), header. ("Dashboard" now names the **Statistics overlay** it launches — don't use it for the bar itself.)

**Status bar**: A horizontal strip across the bottom of a **Profile-bound Window**, beneath the workspace stack. Shows the **Active workspace**'s identity (name, root folder, current git branch when the folder is a repository, current **Tab**) on the left, and on the right ambient telemetry — **machine-wide** CPU and memory load (not Abundio-specific; see Flagged ambiguities) — alongside the **Active profile**. Always visible; read-only. Counterpart to the **Overview bar**: the Overview bar (top) carries glanceable agent counts across all opened workspaces plus this **Profile**'s PR counts; the Status bar (bottom) carries *this Window's* workspace context plus system load.
_Avoid_: footer, info bar; do not call the **Overview bar** a "status bar".

**Sidebar**: A collapsible vertical strip of chrome flanking the workspace stack. Two instances, one on each side, with different responsibilities:
- **Left sidebar**: cross-workspace navigation — the **Workspace** list for the Window's **Active profile**. Belongs to the Window, not the Workspace.
- **Right sidebar**: in-workspace tooling for the **Active workspace** — tabs (**Git changes**, **Explorer**, **Search**, **Notes**) plus two **Anchored sections** underneath them, top to bottom: **Commits**, then **Pull Requests**. The tab strip and the Anchored sections are independent: each Anchored section is shared chrome across every tab and collapses independently.

Both sidebars collapse to a 44px icon strip. Open/closed state and (for the right sidebar) the active tab + PR-collapsed state are per-Window. Width is global.
_Avoid_: panel (collides with **Pane** colloquially), drawer, rail.

**Anchored section**: A collapsible panel of the **Right sidebar** that sits below the tab content and stays visible whichever tab is active — **Commits** and **Pull Requests**. Each collapses to its header on its own (per-Window) and is sized by a draggable divider above it (sizes are global). Not a **Section**: that word belongs to the row groups inside the **Git changes tab**.
_Avoid_: panel, pane (collides with **Pane**), sub-panel; bare "section" when the Git changes tab's **Section** could be meant.

**Commits**: The **Anchored section** listing the **Active workspace**'s recent history — the commits in its HEAD, newest first, capped at 200 rows — split in two by a divider named after the base branch (the same base as the `against_base` **Section** and the **Branch stat**). Above the divider are the **Ahead commits**; below it is the **Shared history**. Every commit appears once: first the Ahead commits, then the base's history from where the branch last met it, so a branch that has merged the base in does not interleave the two. The header gives the Ahead count ("3 ahead of main"). On the base branch itself nothing is ahead, so there is no divider and the list is simply its latest commits. When the base cannot be resolved (detached HEAD mid-rebase, a deleted or mistyped base) the list still shows HEAD's history, with no divider and no count, and the header says the base is unknown. A non-git Workspace keeps the section in place with a message, so the layout does not jump between Workspaces. Each row shows the subject, the author's initials and a relative time; expanding a row lists the files that commit touched — for a merge commit, against its first parent — and clicking one opens a read-only **Commit diff pane**. A binary file, or a submodule the commit moved (a pointer into another repository, with no text on either side), is listed but not clickable, though it still carries the **Row menu**. Its right-click menu is read-only like the **Row menu**: Copy hash, and Open on GitHub (disabled, not hidden, when there is no GitHub remote or that remote does not have the commit — the remote linked to and the remote asked "is it pushed?" are always the same one, so a fork checkout never links to the repository that lacks the commit). No git writes — no revert, reset or cherry-pick.
_Avoid_: Branch commits (its old name, from when it listed only the Ahead commits), commits panel, log, unmerged commits ("unmerged" is the **Conflicted section**'s word).

**Ahead commits**: The commits in a Workspace's HEAD that its base branch does not have — `<base>..HEAD`. What the branch would add if merged. Drawn above the **Commits** divider on an accent rail; their count is the Commits header's "N ahead".
_Avoid_: branch commits, my commits, unpushed (a different fact — an Ahead commit may well be pushed), local commits.

**Shared history**: The part of a Workspace's history its base branch also has — the base as the branch last saw it, not the base's current tip. Commits that landed on the base after the branch left it are not in the Workspace and are not shown. Drawn below the **Commits** divider on a grey rail; the rows themselves are full-strength and fully usable.
_Avoid_: main history (the base is not always main), old commits, merged commits.

**Commit diff pane**: A read-only diff **File pane** showing one file as a single commit changed it — the commit's first parent against the commit. Frozen history: never re-read from disk, never touched by the file watcher. Keyed by commit and path, so it opens **alongside** — never replaces — the live working-tree diff pane for the same file, and the same file at two commits gives two panes. One reopened from a saved layout fetches its content once; if the commit is no longer in the repository (rebased away, garbage-collected) the pane says so rather than staying blank.
_Avoid_: history diff, commit view.

**PR scope**: How wide a net one of the **Pull Requests** section's two sub-sections (Review Requested, My Open PRs) casts over the poller's single account-wide dataset. Three of them, chosen per sub-section from its dropdown and remembered per Window: **All** (every PR on the GitHub account), **Profile** (PRs in repositories the Window's **Active profile** resolves to) and **Repo** (the **Active workspace**'s repository alone). **Profile is the default for a fresh install** — a preference already stored for a sub-section is never rewritten — and the **Overview bar**'s PR chips are pinned to Profile whatever the dropdowns say. Purely a client-side filter — never a different query. A Profile's repository set is *derived*, not stored: each **Workspace** contributes every GitHub `owner/repo` its git remotes point at, so a **Worktree set** collapses to one repository and a fork checkout contributes both its own and its upstream. An empty set means the sub-section shows nothing and says so — it never widens back to All. See ADR-0028.
_Avoid_: PR filter, PR view mode, repo group (collides with **Profile**'s sense of "group").

**Unread PR**: A PR in the **Pull Requests** section whose GitHub notification thread is unread for the user. GitHub owns the flag, not Abundio: it clears when the user opens the PR on github.com, marks it read in their GitHub inbox, or reads it on another device. Abundio keeps no "last seen" state of its own, so a PR read on GitHub is never shown as unread here. The flag covers *any* unread activity on the thread (a push, a merge, a review request), not only comments and reviews. Opening a PR from Abundio marks its thread read on GitHub, so it also leaves the user's GitHub inbox.
_Avoid_: new comments (the flag is not limited to comments), seen/unseen.

**Update**: A newer published Abundio release the running app can fetch and apply via the Tauri updater. App-global, not per-Profile. Lifecycle: *available* → *downloading* → *staged* → *installed on quit*. By default applied only on the next natural quit so live **PTY**s and **Agent** turns survive; an explicit, confirmed "restart now" is the exception. The version check runs in Rust and surfaces in the focused **Window** only; the *staged* state lives in Rust and is app-global, so every **Window** reads the same one. See ADR-0014.
_Avoid_: upgrade, patch, version bump.

**Release notes**: The Markdown body of a **published** GitHub Release — the single source of truth for "what changed", with no `CHANGELOG` in the repository. Rendered in-app rather than linked out: the **Updates section** shows the running version's notes plus every newer release's, and the **What's new card** shows the running version's alone. Fetched from the GitHub API in Rust (one page of 30, newest first, prereleases dropped) and cached app-globally for an hour; drafts are invisible to the unauthenticated API, which is exactly ADR-0014's rule that clicking *Publish* is the gate. An **Update**'s own notes also arrive for free on `UpdateInfo.body`, which is used only as the offline fallback.
_Avoid_: changelog, release body, patch notes.

**What's new card**: The card shown after Abundio starts on a version newer than the last one whose **Release notes** the user saw, and shown again on each later start **until it is dismissed** — `last_seen_version` advances on dismissal, not on display, so a quit or a Window close does not consume it. Bottom-right and non-blocking, like the update prompt, and it takes that corner's priority while it is up. Gated in Rust on `last_seen_version` (the app-global `settings` key-value table) versus the running version, and emitted to the focused **Window** only — the same `emit_to_focused` rule the update prompt uses, and the reason this cannot live in `localStorage`, which is per-webview on macOS. The version is marked seen only once notes were actually fetched, so an offline launch shows nothing and tries again later rather than burning the flag.
_Avoid_: changelog popup, welcome dialog, release dialog.

**Quit route**: One of the three ways Abundio's process ends, each reaching different code. **Menu quit** (Cmd+Q / "Quit Abundio") runs our custom `quit-app` handler *before* windows tear down. **Last-window quit** closes the final **Profile-bound window**, whose `Destroyed` handler calls `exit(0)`, which raises `RunEvent::ExitRequested`. **Dock quit** (Dock icon → Quit, and OS shutdown/logout) is `[NSApp terminate:]`: it raises **only** `RunEvent::Exit`, never `ExitRequested`, and may destroy no windows at all. Anything that must happen at quit — persisting `windows.json`, installing a staged **Update** — has to cover all three or it silently skips one.

**Shell-mode PTY**: A PTY that Abundio has not currently detected as running an Agent — a plain shell. Its counterpart, an **agent-mode PTY**, has its status indicator driven by Agent hooks. A single PTY flips between the two as Agents are launched in it and exit.
_Avoid_: shell pane, terminal mode (a Pane has no mode — its PTY does)

**Agent-mode PTY**: A PTY that Abundio believes is running an **Agent**. It **enters** agent mode three ways: the shell reports a command line that matches a **Watched** Agent (`command_start`), Abundio types an Agent's launch command itself (launch picker, Command palette, auto-relaunch), or any **Agent hook** other than a **Session end** arrives from it. It **leaves** agent mode only when the launching command finished — the Agent *process* is gone — which also forgets the remembered Agent so it does not relaunch. Two signals prove that, one per kind of shell: shell integration's `command_end` (zsh, bash, PowerShell), and for every other shell (fish, nushell, plain `sh`, `cmd.exe`) the backend noticing the shell has no child process left. Both signals come from the shell Abundio spawned, so they only see *its* commands. **Known gap, accepted:** an Agent run from a nested shell — a subshell opened inside the pane (`nix develop`, `poetry shell`, `pipenv shell`, a typed `bash` or `fish`, `tmux`) — still reaches Abundio through its hooks, but its exit is invisible: the outer shell reports only when the inner one exits. Until then the PTY stays in agent mode, and the Agent stays remembered, so it auto-relaunches on the next start. The alternative, letting a Session end drop agent mode there, would bring back the `/clear` bug. An Agent's own "session ended" hook never ends agent mode (see **Session end**).
_Avoid_: agent pane (the mode belongs to the PTY)

**Session end**: An Agent's hook saying its *conversation session* ended — Claude Code's `SessionEnd`, Copilot's `sessionEnd`, OpenCode's `session.deleted`, and the equivalents. It is **not** a process exit: Claude Code and Copilot both fire it on `/clear`, which ends the session and starts a new one in the same process, and Copilot reports `reason: "user_exit"` for `/clear` and `/exit` alike, so the payload cannot tell them apart. A Session end therefore only closes the open **Turn** and lands the pane on **Idle**; the PTY stays an **agent-mode PTY** and its remembered Agent is kept. It also never *adopts* agent mode: it can arrive just after the Agent process exited, and must not put an exited Agent's PTY back into agent mode.
_Avoid_: agent exit, session exit

**File drop**: Dropping one or more OS files (from Finder/Explorer) onto a **terminal pane** inserts their path(s) into that pane's PTY as bracketed-paste input — **never auto-executed**, with a trailing space; multiple files are space-separated. The target is the pane under the cursor, highlighted during the drag, and is focused on drop. The path format is **mode-aware**: a **shell-mode PTY** receives POSIX-single-quoted paths when they contain spaces/special characters (so the path survives as one shell token), while an **agent-mode PTY** receives the raw literal path (so the Agent resolves it). Always on; not gated by any setting. Delivered via Tauri's OS `drag-drop` events — distinct from the mouse-driven **Pane** drag used to reorder panes. The image special-case is **Smart image drop**.
_Avoid_: file paste; "drag and drop" unqualified (collides with pane reordering).

**Smart image drop**: The image special-case of **File drop**, governed by the global `smartImageDrop` setting (Terminal section, on by default). When **exactly one** image file (any raster format Abundio can decode — re-encoded to PNG) is dropped onto an **agent-mode PTY**, Abundio writes the PNG to the OS clipboard and sends the Agent a paste keystroke (`Ctrl+V` / byte `0x16`) so the Agent ingests it as if pasted, instead of inserting the path. It fires for *every* agent-mode pane regardless of whether that Agent can actually read a clipboard image, and does **not** restore the prior clipboard (see Flagged ambiguities). Multi-file drops, non-image files, **shell-mode PTYs**, and the setting being off all fall back to plain path insertion.
_Avoid_: image paste, paste-as-clipboard.

## Relationships

- A published **Release notes** body exists for every **Update**, but not for every running version: a development build, or a release still in draft, has none — which is a different state from "we could not reach GitHub" and is worded differently in the UI.
- The **What's new card** and the update prompt share one corner of a **Profile-bound Window**; at most one is on screen, and the What's new card wins until dismissed.

- Every **Workspace** belongs to exactly one **Profile**; the Workspace ↔ Profile assignment is set at creation and not editable afterwards.
- Each **Profile-bound Window** shows exactly one **Profile**, and each Profile is shown in at most one Window. Opening a new Window requires picking a Profile that is not already shown elsewhere (or creating a new "Untitled" Profile inline from the File menu).
- **Auxiliary windows** (e.g. the **Settings window**) do not own a Profile, are not persisted in `windows.json`, and do not count toward the "last window closing quits the app" rule. Closing every Profile-bound window quits the app even when the Settings window is still open.
- The sidebar of a Window shows only Workspaces in *that Window's* **Active profile**.
- The set of **Opened workspaces** is always a subset of the Window's **Active profile**'s Workspaces — switching Profile *within a Window* closes every Opened workspace in that Window's previous Active profile.
- At least one **Profile** must always exist. Deleting the **Active profile** auto-switches the Window to the first remaining Profile in position order that is not already open in another Window. A Profile cannot be deleted while it is open in another Window; the active Profile cannot be deleted if no unowned profile is available to auto-switch into. Deleting any Profile cascade-deletes its Workspaces.
- The **Active workspace** is always also an **Opened workspace**.
- A Workspace shown in the sidebar may be neither Active nor Opened — it has not been activated this session.
- **Closing** a Workspace removes it from Opened; deleting also removes it from the sidebar.
- A **Worktree set** is derived, not stored: two Workspaces belong to the same set iff their folders are worktrees of the same git repository. Membership and primary-vs-linked status are recomputed from git, never authored by the user. **Add worktree** is offered on any Workspace bound to a repository's *main* worktree — a **Primary worktree** when a set already exists, or a standalone git Workspace not yet in a set (its first add bootstraps the set). **Remove worktree** is a **Linked worktree**-only action that physically deletes that worktree's folder.
- **Worktree setup commands** are configured per main-worktree Workspace (stored on its row, so a repo present in two Profiles keeps an independent copy) and execute only on an in-app **Add worktree**, in the new worktree's focal terminal, before any chosen Agent. They are edited in the **Workspace settings** dialog.
- The **Git changes tab**'s **Conflicted section** is the one section whose rows open a text-mode **file pane** rather than a diff pane — a conflicted file is something you resolve, not something you review. A conflicted file appears simultaneously under Conflicted and under Against-base, because those two sections compare different things.
- A **Merge side pane** belongs to the same **Tab** as its **source pane**, mirrors one index stage of that pane's file, and is removed automatically once the file is no longer unmerged.
- Each **Tab** belongs to exactly one **Workspace**.
- Each **Workspace** has at most one **Note** (one-to-zero-or-one); the Note is deleted with its Workspace.
- Each **Turn** belongs to exactly one **Profile** (stored directly on the row) and references at most one **Workspace** (denormalized by id + name). Lifetime is deliberately asymmetric: deleting a **Profile** cascade-deletes its Turns; deleting a **Workspace** does **not** (so historical totals don't shrink). Turns are grouped into **Sessions** by `session_id`. See ADR-0018.
- Each **Pane** belongs to exactly one **Tab**. A terminal pane holds at most one **PTY**; a file pane holds at most one open file; a preview pane holds neither — it references a **source pane**.
- A **preview pane** and its **source pane** always live in the same **Tab**.
- Abundio derives an **Agent**'s status by observing its **Agent hooks**; a permission-request hook puts the Agent into the **Waiting** state, which clears when the user types into that **Pane**'s terminal.
- **Hook provisioning** runs at several moments, gated by the **Status Hooks setting** and each Agent's **Watched** toggle: at app startup (once per process, however many **Windows** open), on toggling the global setting, on toggling an individual Agent (its hooks are installed or removed to match), and the first time an Agent is launched in a **Pane** if not yet provisioned. The launch-time path may create the Agent's config dir if absent — a launch is explicit intent — whereas startup/toggle never scaffold dirs for Agents the user hasn't run. A newly-installed or newly-enabled Agent therefore gains hooks without an app restart. See ADR-0003.
- Installing an **Update** is deferred to app quit by default: the staged install runs on every **Quit route** before Windows tear down, so it composes with the "last-window-closing quits the app" rule rather than interrupting a running session. The same is true of persisting `windows.json` — the two share the quit-route coverage problem, and any new quit-time work inherits it.
- Abundio derives a **shell-mode PTY**'s status from shell-integration OSC markers (`command_start` / `command_end`) emitted by Abundio's startup hooks; **Working** and **Error** for shells are detected this way (a clean exit returns to **Idle**, with no Ready hop). Without working shell integration the PTY degrades silently to permanent **Idle** (no false signal).
- Abundio derives a **PTY**'s **Status indicator** through the **Status machine**: producers (an **Agent hook**, a shell-integration marker or its process-monitor fallback, a keystroke, a PTY exit, the idle **Tick**) become **Status events**; the pure **status reducer** folds each into the per-PTY status; every change is emitted as a **Status transition** that the UI, notifications, and **Turn** telemetry each project differently. Telemetry rides the *output* (not the input) because the idle backstop — a stuck Working → Ready when a Stop hook was dropped — is a turn boundary with no input event behind it. See docs/plans/status-machine.md.

## Flagged ambiguities

- "Release notes" and "changelog" were used interchangeably — resolved to **Release notes**, and there is deliberately **no** `CHANGELOG` file in the repository. The GitHub Release body is the only place they are authored, so the app reads them over the network at runtime. The consequence is accepted rather than worked around: with no cached copy on disk, an offline user cannot read their own version's notes at all.
- "Show the release notes" does not mean "open the GitHub page". Notes are **rendered in-app** with the Markdown renderer; the link out survives only as a fallback when the fetch fails and as an "older releases" escape hatch. The `#123` shorthand in a release body is *not* linked by the API — the app linkifies PR references itself, and deliberately leaves `@mentions` and commit SHAs as plain text.
- "The updater in the Settings window" is not a thing — there is **one** updater, app-global and owned by Rust. The **Settings window** and the update prompt card are two *views* of the same `UpdaterState`, differing only in which buttons they offer. A behavioural difference between them is therefore always either (a) a missing button or (b) a **Quit route** that skips the install — never "two updaters".
- "Quit" was used as if it were one event. It is three (**Quit route**), and Tauri's `RunEvent::ExitRequested` fires for only two of them — it is emitted when the last window is *destroyed*, which **Dock quit** never does. `RunEvent::Exit` is the only event common to all three.
- "Window" has two meanings in Abundio code and conversation, and they are unrelated: the **Window** entity (OS-level application window — a Tauri `WebviewWindow`) is canonical; the historical use of "window" to mean a **Pane** is forbidden. When discussing Panes, use "pane" or "split"; when discussing Windows, capitalise to disambiguate where ambiguity would arise.
- "Profile" in Abundio refers exclusively to the top-level grouping entity. Despite borrowing the word from VS Code / browser conventions (where it bundles identity + settings), Abundio's Profile currently only groups Workspaces — appearance, agents and GitHub identity remain global. The term was kept against the narrower fit of "Space" or "Group" so that the scope may widen later without renaming.
- "active workspaces" (plural) does not exist — **Active workspace** is a singleton. Colloquial use of the plural is resolved to **Opened workspaces** (the set of workspaces activated this session and still open). The **Overview bar** uses "Opened" as its label for this reason.
- "background loaded workspace" was used to mean both "every sidebar workspace" and "opened-but-not-active workspace" — resolved to the latter (an Opened workspace that is not Active).
- "dormant workspace" is **not** a distinct state — it denotes a sidebar Workspace that is **neither Active nor Opened** (one not activated this session, per the relationship "A Workspace shown in the sidebar may be neither Active nor Opened"). Use that phrasing; "dormant" carries no extra meaning.
- The Left-sidebar context-menu labels **"Unload Workspace"** and **"Close Workspace"** are *inverted* relative to this glossary's verbs. "Unload Workspace" performs the glossary's **Close** (`closeWorkspace`: tear down the Workspace's PTYs, drop it from **Opened**, keep its row in the sidebar); "Close Workspace" performs the glossary's **delete** (`deleteWorkspace`: also remove the row and DB record). Resolved: **Close** and **delete** are canonical in prose; "Unload"/"Close Workspace" are UI-only wording kept as-is. The "Unload Workspace" confirm dialog echoes the button's "Unload" wording and fires only when an Agent is **Working** or a shell command is in progress in the Workspace (a **Waiting** agent does not trigger it) — narrower than the tab-close confirm, which fires on a merely *attached* Agent.
- "panel" is used colloquially to mean both a **Pane** and a **Sidebar** — resolved by retiring "panel" from canonical use. Side chrome is always a **Left sidebar** or **Right sidebar**; the historical names "git panel" / "git changes panel" no longer fit because the right sidebar hosts Git changes, Explorer, Search, and PRs together. When referring to a section *within* the right sidebar, use its tab name ("Git changes tab", "Explorer tab", "Search tab") or "PR section".
- The **Git changes tab**'s sections *look* like one taxonomy but are two. Four of them are **pairs of git endpoints** being compared, forming a pipeline — `untracked` → `unstaged` (index vs worktree) → `staged` (HEAD vs index) → `against_base` (merge-base..HEAD, committed history only). **Conflicted** is not a fifth stop on that path: it is a *state* that suspends the pipeline, and an unmerged path has no stage 0 to diff, so it has no honest staged/unstaged entry at all. Resolved deliberately: Conflicted is listed as a section because that is where users look for it, and a conflicted file appearing in *both* Conflicted and Against-base is correct rather than a duplicate — dropping it from Against-base would silently shrink the branch review mid-merge and restore it afterwards, for reasons unrelated to the branch. See ADR-0029.
- "ours"/"theirs" are canonical in **Rust** (git's own index vocabulary — `git checkout --ours` addresses stage 2) and forbidden in the **UI**, which says **Current side**/**Incoming side**. The boundary is the IPC layer. The reason is that a rebase inverts them: git replays your commits onto upstream, so "theirs" is your own commit. User-visible text for a marker-less conflict (delete/modify, add/add) therefore names **neither** side — those files carry no marker labels to read the truth from, and phrasing it correctly would otherwise require detecting merge vs rebase vs cherry-pick just to write a sentence. See ADR-0029.
- "Detection" meant three things at once: an Agent being **Installed** on `$PATH`, an Agent being **Watched** (the per-Agent toggle, whose Settings copy called itself "detection"), and the runtime title/process match that flips a **PTY** into agent mode. Resolved: the first two are **Installed** and **Watched**; only the third is still called detection, and only in the PTY-mode sense.
- "Session end" was treated as "the Agent exited", which dropped agent mode on every `/clear` (first fixed for Claude Code alone, then found again in Copilot). Resolved: a **Session end** is only a session boundary; leaving agent mode belongs to the Agent process exiting alone.
- "shell mode" / "terminal mode" were both used for a PTY not running an Agent — resolved to **shell-mode PTY**; the mode belongs to the PTY, not the Pane.
- The amber state is canonically **Working** in this doc — applying to both agent-mode and shell-mode PTYs — but `PtyActivityState` in code still uses the string `"active"`. Renaming the code value to `"working"` would remove the collision with **Active workspace** and align with the broadened glossary; scheduled as part of the **Status machine** refactor, whose new reducer state type adopts the canonical names (see docs/plans/status-machine.md).
- The **Status bar**'s CPU/memory readout is **machine-wide**, not Abundio's own footprint, despite the original request being "usage of the application". Per-app attribution was investigated and rejected: Abundio's heavy memory lives in WebKit content processes that macOS reparents to `launchd` and only re-groups via private APIs that proved missing or contaminated on the target machine. Resolved to system-wide load (see ADR-0011).
- "no workspace selected/opened" was used loosely for the **Pull Requests** section's empty state — resolved to "the set of **Opened workspaces** is empty" (zero workspaces activated this session), *not* merely "no **Active workspace**". In that state there is no **Active workspace** to point the **Repo** **PR scope** at, so a section whose stored preference is Repo shows **Profile** instead (the next-narrowest scope, not the noisiest one) and Repo drops out of that section's dropdown; the stored preference is preserved and restored when a workspace reopens. Profile and All are unaffected — Profile reads the **Left sidebar**'s Workspace list, which needs nothing Opened. The *mechanism* is not a per-workspace fetch: an app-global poller always runs **one** account-wide `gh api graphql` query (from the home directory) and every scope is a **client-side filter** over that single dataset. This still reverses ADR-0005's original concession of "no PR data until a Workspace opens" — see ADR-0005, ADR-0019, ADR-0028. (Before ADR-0028 this state forced the account-wide `-all` view and locked the dropdown.)
- Copilot's **Waiting** is driven by the `notification` hook, not `permissionRequest`. `permissionRequest` fires for every permission-gated tool even when auto-approved (order `preToolUse → permissionRequest → postToolUse`), so it can't tell a genuine block from autopilot at request time. Copilot's `notification` hook instead carries a `notification_type`, and a real permission prompt arrives as `notification_type: "permission_prompt"` (only on genuine prompts — empirically clean despite github/copilot-cli#2586). Abundio provisions the `notification` hook with a `matcher: "permission_prompt"` so only real prompts reach it, then maps `notification → Waiting` directly. The two prompt-tools that emit no `notification` (`exit_plan_mode`, `ask_user`) keep an immediate-Waiting via a `preToolUse` hook matcher-scoped to just those two tool names. The Waiting icon is held against the prompt's own render output by a `recordOutput` guard (agent-mode Waiting is cleared only by a keystroke or the next hook — the invariant **Idle**/`markIdle` already documents) and cleared on the user's keystroke (digit/Enter → Working, ESC → Idle) or `agentStop`. Other Agents enter **Waiting** immediately on a permission/input hook — theirs fires only on a genuine prompt. See ADR-0015.
- **Smart image drop** fires the clipboard trick for *every* **agent-mode PTY**, not only Agents that can read a clipboard image. Empirically only Claude Code (macOS) and Gemini CLI ingest a clipboard image on `Ctrl+V`; Codex, Copilot, OpenCode and Aider do not. Dropping an image on one of those Agents therefore overwrites the user's clipboard and silently attaches nothing — no path is inserted as a fallback. This was chosen deliberately, trading per-Agent correctness for a single simple gate (agent-mode vs shell-mode); revisit if per-Agent capability gating becomes worthwhile. The clipboard is intentionally **not** restored afterwards because the Agent reads it asynchronously after the keystroke, so any restore would race the read.
- The **Statistics overlay** is **Profile-scoped** (it counts only the Window's **Active profile**'s **Turns**) even though it is launched from the **Overview bar**, whose agent and shell counts aggregate across all opened workspaces. The button is global; the surface it opens is per-Profile. Resolved deliberately — the overlay behaves like in-Profile tooling, not account-wide chrome. Since ADR-0028 the bar's **PR** counts pull the same way (Profile-scoped), so the overlay is no longer the lone exception. See ADR-0018, ADR-0028.
- The **Overview bar**'s PR counts are **Profile-scoped** while GitHub PR **notifications** stay **account-wide** — a deliberate asymmetry, not an oversight. You can be notified about a PR the panel and chips won't show. The reason is delivery, not taste: the Rust poller emits `pr-changes` to exactly *one* **Window** (ADR-0019), so filtering it per-Profile in the frontend would not reroute the notification to the Window whose Profile owns that repository — it would drop it entirely. Revisit if the poller ever learns the Window↔Profile map. See ADR-0028.
- A **Turn**'s line counts are a **per-Turn working-tree diff**: the Workspace's working tree is snapshotted as a git tree at Turn start and Turn end, and the additions/deletions *between those two snapshots* are the lines the Turn changed — *not* a precise tally of the lines the Agent itself typed. They capture the Turn's **net effect** on the files and are approximate: within-Turn redos collapse, a manual edit between the prompt and the Turn's first write (or a brief start-snapshot race) can shift them, and a revert correctly counts as deletions. (A brand-new file the Agent creates is counted as additions from the moment it exists — even before `git add`. Snapshotting mutates only an *in-memory* git index — never the on-disk staging area. The invariant this protects is that Abundio writes the index only on **explicit user action**, never as a side effect of telemetry, polling or rendering; the one deliberate writer is **Resolve & stage** (ADR-0029) — writing loose objects that `git gc` later reaps.) They are recorded as **NULL ("unmeasured")** when two Turns overlap in the same **Workspace** (the shared working tree can't be split between them), when the Workspace isn't a git repo, or when the start snapshot is unavailable. The UI labels this ("changed during turns", "unmeasured"). See ADR-0018, ADR-0021.
- **File drop** on Windows is shell-aware for **Git Bash** but not yet for cmd.exe/PowerShell. A drop onto a Git-Bash (MSYS) pane converts Windows paths to their `/c/…` unix form (so the path resolves, and POSIX single-quoting is then correct). cmd.exe and PowerShell panes keep their native `C:\…` style (correct), but still receive POSIX quoting, which is **wrong** for them (cmd single quotes aren't metacharacters; PowerShell rejects the `'\''` escape) — tracked as `TODO(windows)` in `lib/fileDrop.ts`, to be fixed with per-shell quoting. The pane's shell kind is derived from the user's `shellPath` setting, falling back to the Rust-resolved System Default (`default_shell` command); a pane spawned before the user last changed that setting could be misclassified (rare, since the setting is global and seldom changed mid-session).
