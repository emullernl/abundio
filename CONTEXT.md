# Abundio

GPU-accelerated terminal multiplexer. The user opens one or more application Windows; each Window shows one Profile; each Profile owns a set of Workspaces; each Workspace runs its own pane layout and PTY processes.

## Language

**Window**: A single OS-level application window (Tauri `WebviewWindow`). Windows come in two kinds:
- **Profile-bound window**: owns exactly one **Profile** (one-to-one, exclusive — a Profile is open in at most one such Window at a time). Created via File → New Window with Profile. Appears in `windows.json` for restoration across launches and counts toward the "last-window-closing quits the app" rule. Labels follow the pattern `main` (the first window) or `window-<uuid>` (additional windows).
- **Auxiliary window**: serves a global purpose unrelated to any single Profile. Currently only the **Settings window**. Does not own a Profile, is not persisted in `windows.json`, and does not count toward the quit rule. Uses a stable singleton label (`settings`).

The label is the stable identifier across launches — both Abundio's own `windows.json` and `tauri-plugin-window-state` key per-window data by it.
_Avoid_: viewport, app instance, frame; do **not** use "window" to mean a **Pane** (see Pane).

**Settings window**: The singleton auxiliary **Window** labelled `settings`. Opens (or focuses if already open) via File menu, Cmd+,, or the "Manage Profiles…" deep-link; with no section requested it lands on Theme. Edits the *global* profile registry — has no active Profile of its own. Every global setting changed here propagates live to all open Profile-bound windows via a Tauri event broadcast, except a small denied set — the drag-derived sidebar widths, the activity byte threshold, and the last-opened dev environment breadcrumb — which are global but too noisy to broadcast. The propagation is bidirectional: a command-palette toggle in a Profile window reaches Settings too. See ADR-0008.
_Avoid_: preferences window, options dialog.

**Settings section**: One leaf page of the **Settings window**, and the unit its deep-link addresses. Eight of them, presented under three non-clickable group captions: *Appearance* (**Theme**, **Fonts**), *Panes* (**Terminal**, **Editor**), *Application* (**Agents**, **Profiles**, **GitHub**, **Updates**). The section ids cross the Rust→JS boundary as `open_settings_window { section }` — encoded in the window URL on a cold open, emitted as a `settings-set-section` event when the window is already open — so they are vocabulary, not implementation detail. **Group captions are not addressable**: there is no `appearance` section. Ids from before the regroup (`terminal-font`, `ui-font`, `shell`) still resolve, in `lib/settingsSections.ts`.
_Avoid_: settings tab, settings panel (see the **Workspace settings** entry).

**Settings ▸ Editor**: A UI label, not a domain term — the section configures both the **file pane** (wrap long lines) and the **preview pane** (whether opening a markdown file spawns one). It is named for what users call Monaco, and is deliberately not folded into Appearance: auto-opening a preview is layout behaviour, not look. The **Preview color mode** stays on the preview's title bar per ADR-0013; the section points at it rather than duplicating it.

**Profile**: A top-level grouping of Workspaces — a named bundle the user uses to organize unrelated bodies of work (e.g. "Work", "Personal"). Each **Workspace** belongs to exactly one Profile and cannot be moved between Profiles after creation. The only per-Profile data today is the Workspace list; appearance, custom agents and GitHub identity remain global, and environment variables are per-**Workspace** (see Environment Bundle). Scope is intentionally narrow so the term may broaden later. A Profile is bound to at most one **Window** at any moment.
_Avoid_: space, group, namespace, context

**Active profile**: The single Profile currently shown in a given Window. Per-Window singleton — Window A's active profile is independent of Window B's, but a Profile cannot be active in two Windows at the same time. Switching Profile closes every Opened workspace in the previous Active profile of *that Window* (with a confirm dialog when any are open). Persisted across restarts per-Window.
_Avoid_: current profile, selected profile, focused profile

**Default profile**: The Profile created at migration time to host pre-existing Workspaces. After migration it has no permanent specialness: it can be renamed, and it can be deleted as long as another Profile exists. The system invariant is "at least one Profile must always exist" — not "the Default must exist".
_Avoid_: primary profile, root profile, main profile

**Workspace**: A folder-bound container with its own pane layout, tabs, and PTY processes. Belongs to exactly one **Profile**.
_Avoid_: project, folder

**Active workspace**: The single Workspace currently selected and visible to the user *within a Window*. Per-Window singleton (`useWorkspaceStore.activeWorkspaceId` — each Window has its own JS context and so its own store instance).
_Avoid_: selected workspace, current workspace, focused workspace

**Opened workspace**: A Workspace the user has activated at least once *in its Window* and has not closed. Tracked per-Window by `usePtyActivityStore.openedWorkspaceIds`. PTY processes and file watchers stay alive for these even when not the Active workspace.
_Avoid_: loaded workspace, mounted workspace

**Background workspace**: An Opened workspace that is not currently the Active workspace. Not a separate state — derived as `openedWorkspaceIds \ {activeWorkspaceId}`.

**Environment Bundle**: A named, ordered set of environment variables owned by a **Workspace** (e.g. `default`, `production`). At most one Bundle per Workspace is the **Injected bundle**; the rest are **On-demand bundles**, and a Workspace may have no Injected bundle at all. Values are encrypted at rest under a single **Master key**; variable *names* are stored in plaintext so the settings list renders without touching the credential store. A Workspace's first variable creates a Bundle named `default` automatically. See ADR-0024.
_Avoid_: env group, env set, env profile (collides with **Profile**), secret store, vault

**Injected bundle**: The Bundle — at most one per Workspace, possibly none — whose variables are placed into the environment of every PTY the Workspace spawns. Set with the green injection toggle beside the bundle row in workspace settings — turning it off leaves every Bundle on-demand — and named by a read-only green pill in the status bar. Changing it affects only *future* terminals — existing PTYs keep the environment they were spawned with until explicitly restarted.
_Avoid_: active bundle, default bundle (`default` is a name, not a role — any Bundle can be the Injected bundle)

**On-demand bundle**: A Bundle that never enters any process environment on its own. Read only through the `abundio-env` helper from inside a pane, typically `abundio-env run <bundle> -- <command>`. This is where credentials that should not be visible to every terminal in the Workspace live.
_Avoid_: manual bundle, inactive bundle

**Master key**: The single 32-byte AES-256-GCM key, held in the OS credential store, that seals every environment variable value. One key per user per machine, not per Workspace or per Bundle. When it cannot be read, environment variables are simply unavailable — terminals still open.
_Avoid_: encryption key, secret key, passphrase

**Shadow variable**: An `ABUNDIO_ENV__<NAME>` copy of an injected variable, set at spawn and re-exported by Abundio's wrapper rc *after* the user's own rc has been sourced, then unset. Its only purpose is precedence: without it an `export` in `.zshrc` would silently beat the Workspace's value. Never visible in a settled shell.
_Avoid_: temp variable, mirror variable

**Inherited variable**: A variable a **Linked worktree** sees because it exists in its **Primary worktree**'s Bundle of the same name. Not a copy — it is read through at spawn time, so editing it in the primary updates every linked worktree. Saving an inherited variable in a linked worktree creates an **Override**: an own row that shadows the inherited one by name, leaving the primary untouched.
_Avoid_: shared variable, parent variable

**Worktree set**: A group of Workspaces that are git worktrees of the same repository — one underlying repository, different branches checked out into different folders, each folder its own Workspace. Rendered as a single visually-distinct cluster in the **Left sidebar**; never a separate stored entity and never a **Profile**. Derived live from git, not persisted: two Workspaces belong to the same set iff their folders are worktrees of the same repository. A repository present only through its main worktree forms no set — the cluster chrome appears only once two or more worktrees of one repository exist as Workspaces. Within a set the **Primary worktree** is always rendered first, followed by the **Linked worktrees**.
_Avoid_: worktree group, repo group (collides with **Profile**'s sense of "group"), worktree cluster.

**Primary worktree**: The Workspace bound to a repository's *main* working tree (git's "main worktree"). Exactly one per **Worktree set**, always rendered first within it. **Add worktree** is offered here — and equally on a standalone git Workspace whose folder is a main worktree but has no set yet; that Workspace simply isn't *called* a Primary worktree until its first linked worktree exists.
_Avoid_: main worktree (git-side synonym, ok colloquially), root worktree.

**Linked worktree**: A non-primary Workspace in a **Worktree set** — a working tree git links to the repository's main one (git's own term for the non-main worktrees). The only Workspace on which **Remove worktree** is offered; removing it deletes that worktree's folder from disk.
_Avoid_: secondary worktree, child worktree.

**Folded set**: A **Worktree set** whose **Linked worktree** rows are hidden in the **Left sidebar**, leaving only its **Primary worktree** row — which then carries a **hidden rollup**. A per-**Window** view preference, kept in `windowUiStore` keyed by the set's git-derived group key, so two Windows showing the same repository can disagree. Deliberately *not* called "collapsed": that word already means the Left sidebar itself is narrow (`sidebarCollapsed` / `CollapsedStrip`), and folding is honoured in both sidebar widths. A folded set never hides the **Active workspace** — activating a hidden member unfolds the set.
_Avoid_: collapsed set (collides with the narrow sidebar), closed set, hidden worktrees.

**Hidden rollup**: The status a **Folded set**'s Primary row shows *on behalf of the members it is hiding* — one status icon at the highest precedence among them (the `computeWorkspaceDotStatus` chain: error > waiting > ready > active > opened > never-opened), plus the count of hidden members. It covers the hidden **Linked worktrees** only, never the Primary itself, whose own status icon keeps its ordinary meaning in the row's left slot — so the icon beside a name always describes the Workspace that row activates. Folding changes what is *drawn*; it never changes what is *notified* (OS notifications from a hidden worktree fire exactly as they do unfolded) and never suppresses the underlying activity tracking.
_Avoid_: set status, aggregate status, group dot (the per-Pane indicator is a **status icon**, never a "dot").

**Workspace settings**: A per-Workspace dialog opened from the **Left sidebar** context menu (`Workspace settings…`). Hosts the Workspace rename and — only for **main-worktree** Workspaces (a **Primary worktree**, or a standalone main worktree) — the **Worktree setup commands** box; Linked worktrees and non-git Workspaces see the rename field alone. A plain in-window dialog, *not* the **Settings window** (which is a global, OS-level auxiliary Window editing the profile registry); Workspace settings edits one Workspace's own row.
_Avoid_: preferences, workspace config, settings panel (collides with **Settings window**).

**Worktree setup commands**: An ordered list of shell commands stored on a **main-worktree** Workspace's row and run in a newly created worktree's focal terminal immediately after an in-app **Add worktree** — and only then. A worktree created via the CLI and surfaced by live-sync is added unopened and runs nothing. The commands are sent as literal shell input (one line per command, the shell serializing them), ahead of any Agent chosen in the Add worktree dialog. Not a git "hook" and unrelated to **Agent hooks** or **Hook provisioning**.
_Avoid_: worktree hook, setup hook, post-create hook, init script.

**Pane**: A leaf slot within a Workspace tab. Panes form a recursive binary split tree (`PaneNode`). A Pane is one of: a **terminal pane** (holds a PTY), a **file pane** (holds an open file), or a **preview pane** (renders another pane's content).
_Avoid_: panel, window, split

**Mouse-reporting pane**: A **terminal pane** whose foreground program has asked to receive the mouse itself (DECSET 9/1000/1002/1003 — the GitHub Copilot CLI turns on 1003 at startup and keeps it on for the whole session; Claude Code never does). In such a pane the mouse belongs to the program, not to Abundio: plain click-drag no longer selects text, because xterm hands its selection service over for the duration. Two gestures are reserved for the user regardless. **Modifier-drag selects** — Option+drag on macOS, Shift+drag on Windows/Linux — and the **right button is always Abundio's**, opening the pane context menu rather than reaching the program. The menu's *Send Right Click to Terminal* item, offered only in a mouse-reporting pane, hands that one click through for programs that want it (tmux with mouse mode). While a selection is up, pointer movement is withheld from the program too — otherwise its own movement reports would wipe the selection before the user could copy it. Both reservations are scoped to this kind of pane: where nothing is reporting the mouse there is no selection at risk, and withholding events would only starve the terminal's own link-hover detection.
_Avoid_: mouse mode, mouse capture, tracking pane

**File pane**: A Pane that holds one open file — rendered as a Monaco editor (text), diff view, or image viewer depending on file type. Identified by its `filePath`. A diff-mode File pane and a text-mode File pane for the same underlying path are tracked independently (keyed `path` vs `diff:path`) and can be open simultaneously — e.g. the **Git changes tab**'s "Open File" action opens the latter without closing the former, and each stays in sync with on-disk changes via the file watcher independently of the other.
_Avoid_: editor, viewer

**Section** (Git changes tab): A group of rows defined by a **pair of git endpoints** being compared — `untracked`, `unstaged` (index vs worktree), `staged` (HEAD vs index), `against_base` (merge-base..HEAD, committed history only). The **Conflicted section** is the deliberate exception: a *state*, not an endpoint pair. See the flagged ambiguity below.
_Avoid_: group, category, bucket.

**Conflicted section**: The first **Section** of the **Git changes tab**, listing the repository's unmerged paths. Sourced from the git index's conflict stages, not from a status walk; its rows carry no line counts, because an unmerged path has no stage 0 and so no honest numstat. Clicking a row opens an editable **file pane** — the only section whose rows do not open a diff pane.
_Avoid_: merge section, conflicts panel, unmerged panel.

**Merge view**: A transient multi-pane arrangement for one conflicted file — read-only **Current side** and **Incoming side** panes above the editable file pane holding the file itself, with an optional **Base** pane. Toggled from the conflict toolbar; torn down automatically once the path is no longer unmerged. Not a distinct editor — ordinary **Panes** in the tab's split tree. See ADR-0030.
_Avoid_: merge editor, 3-way editor, conflict editor, merge pane.

**Merge side pane**: A read-only **Pane** showing one index stage of its **source pane**'s conflicted file. Owns no file — it mirrors a stage, the way a **Preview pane** mirrors a buffer, and shares that pane's derived shape (ADR-0001).
_Avoid_: stage pane, side editor, ours pane, theirs pane.

**Conflict block**: One `<<<<<<< / ======= / >>>>>>>` region within a file's text, comprising a **Current side** and an **Incoming side**, plus an ancestor side when the user's `merge.conflictStyle` is diff3/zdiff3. Abundio recognises a marker by git's own rule — exactly seven characters at column 0 followed by a space or end-of-line — so the two never disagree about what is conflicted.
_Avoid_: hunk (a diff term), conflict hunk, merge chunk, conflict region.

**Current side / Incoming side**: The two halves of a **Conflict block**, named after the labels git writes into the markers. Deliberately *not* "ours"/"theirs", which invert during a rebase (git replays your commits onto upstream, so stage 2 is the upstream side). Those names stay in Rust, where they are git's index vocabulary; the IPC layer is the boundary.
_Avoid_: ours, theirs, local/remote, left/right, mine/yours.

**Resolve & stage**: The only write Abundio performs on a conflict — save the buffer, then `git add` the path. It does not finish the operation; `git merge --continue` (or the rebase/cherry-pick equivalent) stays with the user in a terminal **Pane**. See ADR-0029.
_Avoid_: merge, finish merge, complete merge, commit the merge.

**Preview pane**: A Pane that renders a live, read-only rendering of its **source pane**'s markdown buffer — including Mermaid diagrams. Owns no file of its own; it mirrors. Created beside a file pane when a markdown file is opened. Its appearance is governed by the **Preview color mode**.
_Avoid_: render pane, markdown viewer

**Preview color mode**: A global, persisted user preference governing every **Preview pane**'s appearance. Binary: **follow theme** (the default — the preview adopts the active theme's *actual colours*: its canvas, text, borders, links and accents match the rest of the UI) or **printed paper** (forced pure-white "document" look regardless of theme). There is no forced-*dark* state — a dark preview arises only because the active theme is dark. Toggled from the preview's title bar — Settings ▸ Editor points at that toggle rather than duplicating it. Follow-theme remaps the document **surface** only; code-block **syntax-highlighting** token colours stay at the rendering library's light/dark defaults (themes carry no syntax palette). **Print** always renders on white paper, ignoring this preference. See ADR-0013.
_Avoid_: preview theme, dark mode

**Source pane**: The file pane a preview pane is bound to (`sourcePaneId`). The preview reflects this pane's unsaved buffer and follows it when a new markdown file is opened in it.

**Tab**: A named pane layout within a Workspace. Each tab has its own root `PaneNode`.
_Avoid_: view, screen

**Note**: A single per-Workspace rich-text scratchpad (free text + checklists), edited in the right sidebar's Notes tab and stored as TipTap JSON. Exactly one per Workspace; autosaved. See ADR-0012.
_Avoid_: memo, scratchpad, comment

**PTY**: A pseudo-terminal process bound to a Pane. Identified by a `ptyId` string. Spawned on first render; IDs from previous sessions are cleared on load.
_Avoid_: terminal process, shell

**Agent**: A detected AI coding CLI tool (Claude Code, Copilot, Gemini CLI, Aider, Codex, OpenCode, Qwen Code, Kimi Code, Grok Build) that can be launched inside a Pane. Detected by scanning `$PATH`; not spawned until the user requests one.

**Turn**: One unit of Agent work — from a prompt submitted (turn-start hook) to the turn finishing or failing (turn-finished / turn-failed hook), or, when neither hook ever arrives, to a **Presumed end** inferred from silence (ADR-0027). If the Agent spawned background **Subagents** that outlive the turn-finished hook, the Turn extends until the last of them stops — delegated work is the Turn's work, so its duration and **Working** time include the subagent tail. A new prompt always cuts the extension short: turns never overlap, so a Subagent surviving into the next Turn accrues its remaining time there (accepted imprecision). The extension applies only to a Turn that *finished* — a **Turn failure** has no tail: its Subagents are dropped when the user acknowledges the **Error**, so an orphaned set can't hold the next Turn's turn-finished hook (ADR-0022, ADR-0026). A **Mid-turn failure** does not end the Turn at all. The atomic record for agent telemetry: one row per Turn in the `agent_turn` table, carrying its duration, **Working**/**Waiting** time, permission/tool/error counts, and the lines it changed. See ADR-0018.
_Avoid_: run, request, interaction (and never "running" — collides with **Working**).

**Subagent**: A worker an **Agent** spawns to delegate part of a **Turn** (Claude/Codex/Qwen/Kimi subagent hooks, Grok `SubagentStart`/`SubagentStop` with a `subagentId`, Copilot `subagentStart`/`subagentStop`, OpenCode child sessions with a `parentID`). Abundio observes only its start/stop lifecycle, and only to hold the parent PTY in **Working** until all Subagents finish — a Subagent has no Pane, no status icon, and no telemetry row of its own.
_Avoid_: background agent (not all are background), task (collides with OpenCode's task tool), child session (OpenCode-specific).

**Session**: The span of one Agent process in a Pane — from launch to `SessionEnd`/exit — comprising one or more **Turns**. Not a stored entity: it's a `session_id` stamped on each Turn so the **Statistics overlay** can group a session's Turns and answer "how long was the agent running". See ADR-0018.
_Avoid_: conversation, run.

**Statistics overlay**: A per-**Window**, full-area surface that covers the **workspace stack** (terminals stay alive behind it via the portal registry) to show agent **Turn** telemetry — working-vs-wall-clock time, lines changed, per-agent and per-workspace breakdowns, an activity heatmap, and recent Turns — for the Window's **Active profile** over a selectable range (week/month/year/all). Launched from the one interactive control on the **Overview bar**; closed with its own button or Esc. Profile-scoped, so it refetches when the Active profile changes. See ADR-0018.
_Avoid_: dashboard, stats panel (collides with retired "panel"), stats view/screen (collides with **Tab**).

**Agent hook**: A lifecycle event an Agent emits — prompt submitted, permission requested, turn finished, turn failed — that Abundio observes (via the Agent's own hook system) to drive the status indicator. Abundio only observes; it never alters the Agent's behaviour. Distinct from **Hook provisioning** (the edits Abundio writes so these events reach it).
_Avoid_: callback, event listener

**Hook provisioning**: The set of edits Abundio writes into an Agent's *own* configuration so that Agent emits its **Agent hooks** to Abundio — distinct from the hooks themselves, which Abundio only observes. Comprises the relay scripts in Abundio's data dir plus, per Agent, either entries merged into a co-owned config (e.g. `~/.claude/settings.json`, `~/.gemini/settings.json`, `~/.qwen/settings.json`, `~/.kimi-code/config.toml`) or an Abundio-owned file (e.g. `~/.codex/hooks.json`, `~/.copilot/hooks/abundio.json`, `~/.config/opencode/plugin/abundio.ts`, `~/.grok/hooks/abundio.json` — Grok's personal-scope hooks dir is always trusted, unlike its project-scope hooks which sit behind a folder-trust gate). Gated by the global **Status Hooks** setting; idempotent; removes only Abundio's own entries on disable. See ADR-0003.
_Avoid_: hook injection, hook registration (ok colloquially)

**Status Hooks setting**: The global, opt-out toggle (`agentHooksEnabled`) that turns **Hook provisioning** on or off. On by default. Provisioning of a given Agent is gated by **both** this global toggle and that Agent's own per-Agent toggle (the same one that enables its command detection): an Agent gets hooks only when both are on, and toggling an Agent off removes just its hooks (toggling it back on reinstalls them, if the global toggle is on). The **Provisioning footprint** display in Settings ▸ Agents is read-only — the Agent's existing enable toggle is the per-Agent control.
_Avoid_: hooks preference

**Provisioning footprint**: The concrete, per-Agent record of what **Hook provisioning** has done — which config file is touched, whether Abundio owns that file or merged into a shared one, and which lifecycle events are hooked — surfaced read-only per Agent in Settings ▸ Agents. Each Agent reads as one of: *Registered*, *Not registered*, *Not installed*, *Not supported* (Aider and custom Agents have no hook integration), or *Config error* (the Agent's config is unparseable).
_Avoid_: hook status (ambiguous with the **Status indicator**)

**Waiting**: An Agent state in which the Agent has emitted a permission- or input-request hook and the user has not yet responded in its terminal. Distinct from a finished turn ("ready") — the Agent is stalled mid-turn, not done.
_Avoid_: blocked, idle, stuck

**Working**: A PTY state in which work is in progress — an **Agent** mid-turn (between turn-start and turn-end hooks, not blocked on a permission/input request) or a **shell-mode PTY** between the shell-integration `command_start` and `command_end` markers. Distinct from **Waiting** (agent-only — blocked on the user) and from a finished turn/command. The status indicator differs by mode: agent-Working is the amber broken double-ring spinner (a warm "attention, watch progress" colour), shell-Working is the cyan breathing triple-chevron `>>>` (a cool "neutral throughput" colour — you started the command, no alarm needed).
_Avoid_: active (collides with **Active workspace**), busy, running

**Ready**: An **Agent** state in which the Agent finished its turn cleanly and the user has not yet acknowledged it (by focusing or typing in its pane). Shown as the purple status indicator. Distinct from **Idle** — Ready is a notification, Idle is the rested state after acknowledgement. **Shell-mode PTYs do not have a Ready state**: a clean command exit transitions straight to **Idle** — for a shell, the output that just rendered is itself the "you have something to look at" signal, and a separate notification state would be redundant. Only the **Error** state is surfaced for shells.
_Avoid_: finished, done, complete

**Idle**: A PTY's resting state — no work in progress, and the last finished turn or command (if any) has been acknowledged by the user. Also the default state for a freshly initialised PTY. Shown as the green status indicator.
_Avoid_: inactive, asleep

**Error**: A PTY state in which work failed — an **Agent** emitted a failure hook (or its turn exited non-zero in agent mode), or a **shell-mode PTY**'s last command exited with a non-zero code that isn't a user-stop (130/143). Shown as the red status indicator. Comes in two kinds, distinguished by the **Status event** that caused it and not by the icon (both are red): a **Turn failure** ended the **Turn** — acknowledging it goes to **Idle** and drops any live **Subagents**; a **Mid-turn failure** is an operation inside a Turn that failed while the Agent kept generating — acknowledging it returns the pane to what it was doing (**Working**, or **Waiting** if it was blocked on the user), and the Turn still ends **Ready** if it completes. Only a Turn failure raises a notification. See ADR-0026.
_Avoid_: failed, broken, crashed

**Turn failure**: An **Error** that ended the **Turn** — Claude/Kimi/Qwen `StopFailure`, Grok `Stop{reason:"error"}`, a non-zero PTY exit, or a shell command's non-zero exit. Nothing more is coming, so acknowledging it rests the pane at **Idle**.
_Avoid_: fatal error, hard error

**Presumed end**: A **Turn** boundary Abundio *inferred* from silence rather than observed from an **Agent hook** — the pane went quiet past the idle backstop window and the Agent never said the Turn ended. Recorded under its own end reason so a guessed boundary is never read as an observed one, and timed from the last activity rather than the moment we gave up, so the silence isn't billed as work. Distinct from the **Subagent**-drain backstop, where the turn-finished hook *was* observed and merely held for the tail — there only the timing is fuzzy, not the fact (ADR-0022). See ADR-0027.
_Avoid_: timeout (implies we imposed a limit on the Agent), stale (collides with the Subagent stale prune), abandoned (suggests the user walked away).

**Mid-turn failure**: An **Error** raised by an operation *inside* a **Turn** that the **Agent** carried on past — currently only Copilot's `errorOccurred`, which is always followed by a turn-finished hook. The pane goes red immediately, but the Turn is still open, so acknowledging the red must not claim the Agent went **Idle**. Counted against the Turn's error count without ending it.
_Avoid_: recoverable error (we only know the Agent kept going, not that it recovered), transient error, warning

**Status indicator**: The coloured **status icon** Abundio shows for a Pane — and aggregated up to its Tab and Workspace — reflecting its PTY's current state. The state set differs by **PTY mode**: an **agent-mode PTY** can be Idle / Working / Waiting / Ready / Error; a **shell-mode PTY** can only be Idle / Working / Error (no Ready, no Waiting). Aggregation is also asymmetric: an agent-mode PTY propagates every state to its Tab and Workspace; a shell-mode PTY propagates only Error and otherwise contributes as Idle. So a tab whose only non-idle pane is a shell running a command reads green at the Tab level; a shell whose command errored turns its tab red. Working is shown in **different colours by mode** — amber spinner for an Agent (warm, attention-worthy), cyan breathing chevron `>>>` for a shell (cool, neutral throughput).
_Avoid_: status dot — it renders as an icon (spinner, chevron `>>>`, check, coloured glyph), not merely a dot.

**Status event**: The normalized *input* to the **Status machine** — a single fact about a **PTY** that may drive its status, regardless of source. Producers are an **Agent hook**, a shell-integration OSC marker (or its process-monitor fallback for `ShellType::Other`), a user keystroke, a PTY exit, or the periodic idle **Tick**. Consumed by the **status reducer** (and, at finer grain, by **Turn** telemetry); never observed directly by the UI. See docs/plans/status-machine.md.
_Avoid_: hook (that's one *producer*, not the event), signal (collides with OS signals), activity event.

**Status transition**: The enriched *output* of the **Status machine** — a record `{ ptyId, prev, next, cause }` emitted whenever a PTY's status tuple (icon state + **detection mode** + **Session**) changes, where `cause` is the **Status event** that drove it (or the idle backstop). The single seam every status consumer reads: the **Status indicator**/UI projects `next` → icon colour, notifications project `next ∈ {Ready, Error, Waiting}` + visibility, and **Turn** telemetry projects `cause` + `next`. Carrying `cause` in-band is what removes the former subscriber-ordering races. See ADR-0018, docs/plans/status-machine.md.
_Avoid_: status change event (verbose), state diff.

**Status machine**: The deep module that derives a **PTY**'s status — a pure **status reducer** (`(state, Status event) → state`, fully table-tested, with time supplied via the `Tick` event) plus a **dispatcher** that is the single home for *all* per-PTY status state (the icon state, **detection mode**, **Session**, and the hot activity-heuristic fields previously split across Zustand and out-of-band module Maps), runs the reducer, projects the icon-relevant slice into the store, and emits **Status transitions**. Distinct from the **Status indicator**, which is the *view* of the status the machine computes. Internal state names use the canonical **Working / Waiting / Ready / Idle / Error** (resolving the deferred `active`→`working` code rename). See ADR-0009, ADR-0015, ADR-0020, docs/plans/status-machine.md.
_Avoid_: activity store (the retired `ptyActivityStore` framing), status engine, state manager.

**Overview bar**: A horizontal strip across the top of the app window, between the **Titlebar** and the per-workspace tab row, showing glanceable global counts: **Opened workspaces** (out of total), each of the five **Agent** states (Idle, Working, Waiting, Ready, Error), the three **shell-mode PTY** states (Idle, Working, Error — shells have no Ready or Waiting, see ADR-0009), all aggregated across all opened workspaces, and the user's pending GitHub PR counts (review-requested and own open PRs, both **Profile-scoped** — see **PR scope** and ADR-0028 — and dimmed until the Profile's repository set resolves). The agent and shell counts are derived **live** from `ptyActivityStore` (no cached totals), so every path that closes a Pane/Tab/Workspace must purge that PTY's entries or the counts drift — see ADR-0020. Always visible. Its counts are **read-only** in the sense that it never *mutates* app or workspace state; it carries exactly one **navigation affordance** — a right-aligned button that opens the **Statistics overlay**. The only piece of global chrome that lives between the Titlebar and the workspace stack. See ADR-0005, ADR-0018, ADR-0019, ADR-0028.
_Avoid_: metrics bar, status bar (already taken — bottom of window), header. ("Dashboard" now names the **Statistics overlay** it launches — don't use it for the bar itself.)

**Status bar**: A horizontal strip across the bottom of a **Profile-bound Window**, beneath the workspace stack. Shows the **Active workspace**'s identity (name, root folder, current git branch when the folder is a repository, current **Tab**) on the left, and on the right ambient telemetry — **machine-wide** CPU and memory load (not Abundio-specific; see Flagged ambiguities) — alongside the **Active profile**. Always visible; read-only. Counterpart to the **Overview bar**: the Overview bar (top) carries glanceable agent counts across all opened workspaces plus this **Profile**'s PR counts; the Status bar (bottom) carries *this Window's* workspace context plus system load.
_Avoid_: footer, info bar; do not call the **Overview bar** a "status bar".

**Sidebar**: A collapsible vertical strip of chrome flanking the workspace stack. Two instances, one on each side, with different responsibilities:
- **Left sidebar**: cross-workspace navigation — the **Workspace** list for the Window's **Active profile**. Belongs to the Window, not the Workspace.
- **Right sidebar**: in-workspace tooling for the **Active workspace** — three tabs (**Git changes**, **Explorer**, **Search**) plus an always-anchored **Pull Requests** section underneath the tabs. The tab strip and PR section are independent: the PR section is shared chrome across all three tabs and can be collapsed independently.

Both sidebars collapse to a 44px icon strip. Open/closed state and (for the right sidebar) the active tab + PR-collapsed state are per-Window. Width is global.
_Avoid_: panel (collides with **Pane** colloquially), drawer, rail.

**PR scope**: How wide a net one of the **Pull Requests** section's two sub-sections (Review Requested, My Open PRs) casts over the poller's single account-wide dataset. Three of them, chosen per sub-section from its dropdown and remembered per Window: **All** (every PR on the GitHub account), **Profile** (PRs in repositories the Window's **Active profile** resolves to) and **Repo** (the **Active workspace**'s repository alone). **Profile is the default for a fresh install** — a preference already stored for a sub-section is never rewritten — and the **Overview bar**'s PR chips are pinned to Profile whatever the dropdowns say. Purely a client-side filter — never a different query. A Profile's repository set is *derived*, not stored: each **Workspace** contributes every GitHub `owner/repo` its git remotes point at, so a **Worktree set** collapses to one repository and a fork checkout contributes both its own and its upstream. An empty set means the sub-section shows nothing and says so — it never widens back to All. See ADR-0028.
_Avoid_: PR filter, PR view mode, repo group (collides with **Profile**'s sense of "group").

**Update**: A newer published Abundio release the running app can fetch and apply via the Tauri updater. App-global, not per-Profile. Lifecycle: *available* → *downloading* → *staged* → *installed on quit*. By default applied only on the next natural quit so live **PTY**s and **Agent** turns survive; an explicit, confirmed "restart now" is the exception. The version check runs in Rust and surfaces in the focused **Window** only. See ADR-0014.
_Avoid_: upgrade, patch, version bump.

**Shell-mode PTY**: A PTY that Abundio has not currently detected as running an Agent — a plain shell. Its counterpart, an **agent-mode PTY**, has its status indicator driven by Agent hooks. A single PTY flips between the two as Agents are launched in it and exit.
_Avoid_: shell pane, terminal mode (a Pane has no mode — its PTY does)

**File drop**: Dropping one or more OS files (from Finder/Explorer) onto a **terminal pane** inserts their path(s) into that pane's PTY as bracketed-paste input — **never auto-executed**, with a trailing space; multiple files are space-separated. The target is the pane under the cursor, highlighted during the drag, and is focused on drop. The path format is **mode-aware**: a **shell-mode PTY** receives POSIX-single-quoted paths when they contain spaces/special characters (so the path survives as one shell token), while an **agent-mode PTY** receives the raw literal path (so the Agent resolves it). Always on; not gated by any setting. Delivered via Tauri's OS `drag-drop` events — distinct from the mouse-driven **Pane** drag used to reorder panes. The image special-case is **Smart image drop**.
_Avoid_: file paste; "drag and drop" unqualified (collides with pane reordering).

**Smart image drop**: The image special-case of **File drop**, governed by the global `smartImageDrop` setting (Terminal section, on by default). When **exactly one** image file (any raster format Abundio can decode — re-encoded to PNG) is dropped onto an **agent-mode PTY**, Abundio writes the PNG to the OS clipboard and sends the Agent a paste keystroke (`Ctrl+V` / byte `0x16`) so the Agent ingests it as if pasted, instead of inserting the path. It fires for *every* agent-mode pane regardless of whether that Agent can actually read a clipboard image, and does **not** restore the prior clipboard (see Flagged ambiguities). Multi-file drops, non-image files, **shell-mode PTYs**, and the setting being off all fall back to plain path insertion.
_Avoid_: image paste, paste-as-clipboard.

## Relationships

- Every **Workspace** belongs to exactly one **Profile**; the Workspace ↔ Profile assignment is set at creation and not editable afterwards.
- Each **Profile-bound Window** shows exactly one **Profile**, and each Profile is shown in at most one Window. Opening a new Window requires picking a Profile that is not already shown elsewhere (or creating a new "Untitled" Profile inline from the File menu).
- **Auxiliary windows** (e.g. the **Settings window**) do not own a Profile, are not persisted in `windows.json`, and do not count toward the "last window closing quits the app" rule. Closing every Profile-bound window quits the app even when the Settings window is still open.
- The sidebar of a Window shows only Workspaces in *that Window's* **Active profile**.
- The set of **Opened workspaces** is always a subset of the Window's **Active profile**'s Workspaces — switching Profile *within a Window* closes every Opened workspace in that Window's previous Active profile.
- At least one **Profile** must always exist. Deleting the **Active profile** auto-switches the Window to the first remaining Profile in position order that is not already open in another Window. A Profile cannot be deleted while it is open in another Window; the active Profile cannot be deleted if no unowned profile is available to auto-switch into. Deleting any Profile cascade-deletes its Workspaces.
- The **Active workspace** is always also an **Opened workspace**.
- A Workspace shown in the sidebar may be neither Active nor Opened — it has not been activated this session.
- **Closing** a Workspace removes it from Opened; deleting also removes it from the sidebar.
- A **Worktree set** is derived, not stored: two Workspaces belong to the same set iff their folders are worktrees of the same git repository. Membership and primary-vs-linked status are recomputed from git, never authored by the user. **Add worktree** is offered on any Workspace bound to a repository's *main* worktree — a **Primary worktree** when a set already exists, or a standalone git Workspace not yet in a set (its first add bootstraps the set). **Remove worktree** is a **Linked worktree**-only action that physically deletes that worktree's folder.
- **Worktree setup commands** are configured per main-worktree Workspace (stored on its row, so a repo present in two Profiles keeps an independent copy) and execute only on an in-app **Add worktree**, in the new worktree's focal terminal, before any chosen Agent. They are edited in the **Workspace settings** dialog.
- The **Git changes tab**'s **Conflicted section** is the one section whose rows open a text-mode **file pane** rather than a diff pane — a conflicted file is something you resolve, not something you review. A conflicted file appears simultaneously under Conflicted and under Against-base, because those two sections compare different things.
- A **Merge side pane** belongs to the same **Tab** as its **source pane**, mirrors one index stage of that pane's file, and is removed automatically once the file is no longer unmerged.
- Each **Tab** belongs to exactly one **Workspace**.
- Each **Workspace** has at most one **Note** (one-to-zero-or-one); the Note is deleted with its Workspace.
- Each **Turn** belongs to exactly one **Profile** (stored directly on the row) and references at most one **Workspace** (denormalized by id + name). Lifetime is deliberately asymmetric: deleting a **Profile** cascade-deletes its Turns; deleting a **Workspace** does **not** (so historical totals don't shrink). Turns are grouped into **Sessions** by `session_id`. See ADR-0018.
- Each **Pane** belongs to exactly one **Tab**. A terminal pane holds at most one **PTY**; a file pane holds at most one open file; a preview pane holds neither — it references a **source pane**.
- A **preview pane** and its **source pane** always live in the same **Tab**.
- Abundio derives an **Agent**'s status by observing its **Agent hooks**; a permission-request hook puts the Agent into the **Waiting** state, which clears when the user types into that **Pane**'s terminal.
- **Hook provisioning** runs at several moments, gated by the **Status Hooks setting** and each Agent's own enable toggle: at app startup (once per process, however many **Windows** open), on toggling the global setting, on toggling an individual Agent (its hooks are installed or removed to match), and the first time an Agent is launched in a **Pane** if not yet provisioned. The launch-time path may create the Agent's config dir if absent — a launch is explicit intent — whereas startup/toggle never scaffold dirs for Agents the user hasn't run. A newly-installed or newly-enabled Agent therefore gains hooks without an app restart. See ADR-0003.
- Installing an **Update** is deferred to app quit by default: the staged install runs in the quit path (the `quit-app` menu item / `ExitRequested`) before Windows tear down, so it composes with the "last-window-closing quits the app" rule rather than interrupting a running session.
- Abundio derives a **shell-mode PTY**'s status from shell-integration OSC markers (`command_start` / `command_end`) emitted by Abundio's startup hooks; **Working** and **Error** for shells are detected this way (a clean exit returns to **Idle**, with no Ready hop). Without working shell integration the PTY degrades silently to permanent **Idle** (no false signal).
- Abundio derives a **PTY**'s **Status indicator** through the **Status machine**: producers (an **Agent hook**, a shell-integration marker or its process-monitor fallback, a keystroke, a PTY exit, the idle **Tick**) become **Status events**; the pure **status reducer** folds each into the per-PTY status; every change is emitted as a **Status transition** that the UI, notifications, and **Turn** telemetry each project differently. Telemetry rides the *output* (not the input) because the idle backstop — a stuck Working → Ready when a Stop hook was dropped — is a turn boundary with no input event behind it. See docs/plans/status-machine.md.

## Flagged ambiguities

- "Window" has two meanings in Abundio code and conversation, and they are unrelated: the **Window** entity (OS-level application window — a Tauri `WebviewWindow`) is canonical; the historical use of "window" to mean a **Pane** is forbidden. When discussing Panes, use "pane" or "split"; when discussing Windows, capitalise to disambiguate where ambiguity would arise.
- "Profile" in Abundio refers exclusively to the top-level grouping entity. Despite borrowing the word from VS Code / browser conventions (where it bundles identity + settings), Abundio's Profile currently only groups Workspaces — appearance, agents and GitHub identity remain global. The term was kept against the narrower fit of "Space" or "Group" so that the scope may widen later without renaming.
- "active workspaces" (plural) does not exist — **Active workspace** is a singleton. Colloquial use of the plural is resolved to **Opened workspaces** (the set of workspaces activated this session and still open). The **Overview bar** uses "Opened" as its label for this reason.
- "background loaded workspace" was used to mean both "every sidebar workspace" and "opened-but-not-active workspace" — resolved to the latter (an Opened workspace that is not Active).
- "dormant workspace" is **not** a distinct state — it denotes a sidebar Workspace that is **neither Active nor Opened** (one not activated this session, per the relationship "A Workspace shown in the sidebar may be neither Active nor Opened"). Use that phrasing; "dormant" carries no extra meaning.
- The Left-sidebar context-menu labels **"Unload Workspace"** and **"Close Workspace"** are *inverted* relative to this glossary's verbs. "Unload Workspace" performs the glossary's **Close** (`closeWorkspace`: tear down the Workspace's PTYs, drop it from **Opened**, keep its row in the sidebar); "Close Workspace" performs the glossary's **delete** (`deleteWorkspace`: also remove the row and DB record). Resolved: **Close** and **delete** are canonical in prose; "Unload"/"Close Workspace" are UI-only wording kept as-is. The "Unload Workspace" confirm dialog echoes the button's "Unload" wording and fires only when an Agent is **Working** or a shell command is in progress in the Workspace (a **Waiting** agent does not trigger it) — narrower than the tab-close confirm, which fires on a merely *attached* Agent.
- "panel" is used colloquially to mean both a **Pane** and a **Sidebar** — resolved by retiring "panel" from canonical use. Side chrome is always a **Left sidebar** or **Right sidebar**; the historical names "git panel" / "git changes panel" no longer fit because the right sidebar hosts Git changes, Explorer, Search, and PRs together. When referring to a section *within* the right sidebar, use its tab name ("Git changes tab", "Explorer tab", "Search tab") or "PR section".
- The **Git changes tab**'s sections *look* like one taxonomy but are two. Four of them are **pairs of git endpoints** being compared, forming a pipeline — `untracked` → `unstaged` (index vs worktree) → `staged` (HEAD vs index) → `against_base` (merge-base..HEAD, committed history only). **Conflicted** is not a fifth stop on that path: it is a *state* that suspends the pipeline, and an unmerged path has no stage 0 to diff, so it has no honest staged/unstaged entry at all. Resolved deliberately: Conflicted is listed as a section because that is where users look for it, and a conflicted file appearing in *both* Conflicted and Against-base is correct rather than a duplicate — dropping it from Against-base would silently shrink the branch review mid-merge and restore it afterwards, for reasons unrelated to the branch. See ADR-0029.
- "ours"/"theirs" are canonical in **Rust** (git's own index vocabulary — `git checkout --ours` addresses stage 2) and forbidden in the **UI**, which says **Current side**/**Incoming side**. The boundary is the IPC layer. The reason is that a rebase inverts them: git replays your commits onto upstream, so "theirs" is your own commit. User-visible text for a marker-less conflict (delete/modify, add/add) therefore names **neither** side — those files carry no marker labels to read the truth from, and phrasing it correctly would otherwise require detecting merge vs rebase vs cherry-pick just to write a sentence. See ADR-0029.
- "shell mode" / "terminal mode" were both used for a PTY not running an Agent — resolved to **shell-mode PTY**; the mode belongs to the PTY, not the Pane.
- The amber state is canonically **Working** in this doc — applying to both agent-mode and shell-mode PTYs — but `PtyActivityState` in code still uses the string `"active"`. Renaming the code value to `"working"` would remove the collision with **Active workspace** and align with the broadened glossary; scheduled as part of the **Status machine** refactor, whose new reducer state type adopts the canonical names (see docs/plans/status-machine.md).
- The **Status bar**'s CPU/memory readout is **machine-wide**, not Abundio's own footprint, despite the original request being "usage of the application". Per-app attribution was investigated and rejected: Abundio's heavy memory lives in WebKit content processes that macOS reparents to `launchd` and only re-groups via private APIs that proved missing or contaminated on the target machine. Resolved to system-wide load (see ADR-0011).
- "no workspace selected/opened" was used loosely for the **Pull Requests** section's empty state — resolved to "the set of **Opened workspaces** is empty" (zero workspaces activated this session), *not* merely "no **Active workspace**". In that state there is no **Active workspace** to point the **Repo** **PR scope** at, so a section whose stored preference is Repo shows **Profile** instead (the next-narrowest scope, not the noisiest one) and Repo drops out of that section's dropdown; the stored preference is preserved and restored when a workspace reopens. Profile and All are unaffected — Profile reads the **Left sidebar**'s Workspace list, which needs nothing Opened. The *mechanism* is not a per-workspace fetch: an app-global poller always runs **one** account-wide `gh api graphql` query (from the home directory) and every scope is a **client-side filter** over that single dataset. This still reverses ADR-0005's original concession of "no PR data until a Workspace opens" — see ADR-0005, ADR-0019, ADR-0028. (Before ADR-0028 this state forced the account-wide `-all` view and locked the dropdown.)
- Copilot's **Waiting** is driven by the `notification` hook, not `permissionRequest`. `permissionRequest` fires for every permission-gated tool even when auto-approved (order `preToolUse → permissionRequest → postToolUse`), so it can't tell a genuine block from autopilot at request time. Copilot's `notification` hook instead carries a `notification_type`, and a real permission prompt arrives as `notification_type: "permission_prompt"` (only on genuine prompts — empirically clean despite github/copilot-cli#2586). Abundio provisions the `notification` hook with a `matcher: "permission_prompt"` so only real prompts reach it, then maps `notification → Waiting` directly. The two prompt-tools that emit no `notification` (`exit_plan_mode`, `ask_user`) keep an immediate-Waiting via a `preToolUse` hook matcher-scoped to just those two tool names. The Waiting icon is held against the prompt's own render output by a `recordOutput` guard (agent-mode Waiting is cleared only by a keystroke or the next hook — the invariant **Idle**/`markIdle` already documents) and cleared on the user's keystroke (digit/Enter → Working, ESC → Idle) or `agentStop`. Other Agents enter **Waiting** immediately on a permission/input hook — theirs fires only on a genuine prompt. See ADR-0015.
- **Smart image drop** fires the clipboard trick for *every* **agent-mode PTY**, not only Agents that can read a clipboard image. Empirically only Claude Code (macOS) and Gemini CLI ingest a clipboard image on `Ctrl+V`; Codex, Copilot, OpenCode and Aider do not. Dropping an image on one of those Agents therefore overwrites the user's clipboard and silently attaches nothing — no path is inserted as a fallback. This was chosen deliberately, trading per-Agent correctness for a single simple gate (agent-mode vs shell-mode); revisit if per-Agent capability gating becomes worthwhile. The clipboard is intentionally **not** restored afterwards because the Agent reads it asynchronously after the keystroke, so any restore would race the read.
- The **Statistics overlay** is **Profile-scoped** (it counts only the Window's **Active profile**'s **Turns**) even though it is launched from the **Overview bar**, whose agent and shell counts aggregate across all opened workspaces. The button is global; the surface it opens is per-Profile. Resolved deliberately — the overlay behaves like in-Profile tooling, not account-wide chrome. Since ADR-0028 the bar's **PR** counts pull the same way (Profile-scoped), so the overlay is no longer the lone exception. See ADR-0018, ADR-0028.
- The **Overview bar**'s PR counts are **Profile-scoped** while GitHub PR **notifications** stay **account-wide** — a deliberate asymmetry, not an oversight. You can be notified about a PR the panel and chips won't show. The reason is delivery, not taste: the Rust poller emits `pr-changes` to exactly *one* **Window** (ADR-0019), so filtering it per-Profile in the frontend would not reroute the notification to the Window whose Profile owns that repository — it would drop it entirely. Revisit if the poller ever learns the Window↔Profile map. See ADR-0028.
- A **Turn**'s line counts are a **per-Turn working-tree diff**: the Workspace's working tree is snapshotted as a git tree at Turn start and Turn end, and the additions/deletions *between those two snapshots* are the lines the Turn changed — *not* a precise tally of the lines the Agent itself typed. They capture the Turn's **net effect** on the files and are approximate: within-Turn redos collapse, a manual edit between the prompt and the Turn's first write (or a brief start-snapshot race) can shift them, and a revert correctly counts as deletions. (A brand-new file the Agent creates is counted as additions from the moment it exists — even before `git add`. Snapshotting mutates only an *in-memory* git index — never the on-disk staging area. The invariant this protects is that Abundio writes the index only on **explicit user action**, never as a side effect of telemetry, polling or rendering; the one deliberate writer is **Resolve & stage** (ADR-0029) — writing loose objects that `git gc` later reaps.) They are recorded as **NULL ("unmeasured")** when two Turns overlap in the same **Workspace** (the shared working tree can't be split between them), when the Workspace isn't a git repo, or when the start snapshot is unavailable. The UI labels this ("changed during turns", "unmeasured"). See ADR-0018, ADR-0021.
- **File drop** on Windows is shell-aware for **Git Bash** but not yet for cmd.exe/PowerShell. A drop onto a Git-Bash (MSYS) pane converts Windows paths to their `/c/…` unix form (so the path resolves, and POSIX single-quoting is then correct). cmd.exe and PowerShell panes keep their native `C:\…` style (correct), but still receive POSIX quoting, which is **wrong** for them (cmd single quotes aren't metacharacters; PowerShell rejects the `'\''` escape) — tracked as `TODO(windows)` in `lib/fileDrop.ts`, to be fixed with per-shell quoting. The pane's shell kind is derived from the user's `shellPath` setting, falling back to the Rust-resolved System Default (`default_shell` command); a pane spawned before the user last changed that setting could be misclassified (rare, since the setting is global and seldom changed mid-session).
